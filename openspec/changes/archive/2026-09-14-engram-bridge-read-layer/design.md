## Context

`engram` 自带检索（`observations_fts`，FTS5 `unicode61`）在中文上的 token 是标点之间的整段、默认 AND，所以"能召回的前提是猜中分词"。实测：322 条改写查询 R@10 = **0.0000**（全部返回空）；346 条搜索框式查询 R@10 = **0.0520**（328/346 返回空）；207 条从会话日志提取的探索式真实查询默认命中 118（57.0%），换 `match_mode:"any"` 只救回 26% 的零命中。

已建成并逐项验证一条只读派生读层（回归参照物是 Python 的 `read.py`，不是要逐行移植的模板）。本设计把它工程化进桥，并记录取舍依据。**证据与物证全部留在本仓库之外的本机目录，不进本仓库**（门禁只对文本做内容扫描，二进制夹具能绕过——它拦不住个人数据泄漏）。

读层的形状：候选池是词法（CJK bigram 倒排）加权覆盖率、不设阈值；得分 = `max(归一化余弦_bge[, 归一化余弦_minilm]) + w · field_cov`，`w = 0.20`（P2 调参、P3 留出确认）；软加权不是硬门；筛选**后置**。

两个冻结代理上的检索质量（R@10 / MRR）：

| 臂 | P2 | P3 |
|---|---|---|
| FTS（现状） | 0.0000 / 0.0000 | 0.0520 / 0.0506 |
| bigram 覆盖率 | 0.6677 / 0.4881 | 0.9191 / 0.8335 |
| 仅向量 | 0.7453 / 0.5673 | 0.9133 / 0.8288 |
| **软加权（默认）** | 0.7764 / 0.6453 | **0.9538 / 0.8923** |
| 合并双向量（opt-in） | **0.8634** / 0.6515 | **0.9740** / 0.9156 |

工程验证结论（已在仓库外完成，**不要重新推导**）：一致性读必须显式开事务（无事务对照撕裂 79.4%，单事务 0/3400）；增量更新与全量重建逐行相等（词法）与位相等（向量）；新写入立刻可检索；SQLite 事务本身即足够的原子性单位（SIGKILL 中途杀死后回滚干净、`integrity_check` ok）；词法半边与打分器可移植到 TypeScript 且逐行/逐 rank 相等；加过滤不扰动已验证排序；干净深度 23（这是两个实现之间的差异参数，不是产品限制）。

嵌入层已 spike 并复核：TS + `onnxruntime-web`（纯 WASM）可行，分词 1014/1014、rank 在 depth 10/20/23 各 668/668、热调用中位 2.15 ms（16 线程）/ 8.85 ms（1 线程）。**池化是 CLS（token 0）+ L2 归一化**（`OnnxTextEmbedding` 语义，不是 mean pooling）；**截断承重**（512 上限，346 条里 239 条触顶，精确形式 `[CLS] + 前 510 wordpiece + [SEP]`）；控制字符用 **Cc ∪ Cf ∪ Co**（朴素的 `\p{C}` 会多删 Cn 并破坏分词）。

## Goals / Non-Goals

**Goals**

- 把已验证的读层形状工程化进桥，作为模型唯一的记忆检索入口。
- 检索结果**只读派生**：不写记忆、不改正本、不参与同步备份、可确定性重算、删掉即可。
- 结果可被模型正确使用：截断可见、项目默认隔离、范围不默认过滤、类型不枚举。
- 内容变化在下一次检索可见，且只付增量代价。
- 派生层与运行时的缺失**响亮失败**，绝不升级成会话失败。

**Non-Goals**

- 不做写入端：不改写/删除/新增记忆，不动正本存储与格式，不引入新的同步面。
- 不成为第二个真相来源（本变更同时把 `config.yaml` 的非目标从"不做检索/向量"收窄为此）。
- 不把评测夹具带进仓库（真实语料留在仓库外，仓库单测用合成语料）。
- 本次**不**移除已关断的压缩恢复代码（独立变更）。
- 本次**不**优化新鲜度判定的每查询成本（先照搬已验证形状 + 计量）。

## Decisions

### D1 工具名与替换策略：换名 = `mem_bridge_recall`，`mem_search` 不再注册

机制现成（`UNREGISTERED_ENGRAM_TOOLS` 已用两次，按**精确名**判定，`src/tools.ts:61,69`）。三个候选里选"换名 + 旧名不注册"：沿用 `mem_search` 接管语义会让"检索语义变过没有"在事后无法从工具面回答（同一名字两种实现），而保留原生工具则与已验证的"不要拿 FTS 当 fallback"直接冲突。`mem_` 前缀保留（与其余工具同组、便于按前缀施加可见性限制）；`bridge` 是比通用词更不容易与 engram 自身命名撞车的选择。

**计数要分清两层**（这里我先前写错过两次）：engram 声明 **22** 个；刻意不注册清单**当前有 2 个**（`mem_capture_passive`、`mem_save_prompt`），**本变更加第 3 个**（`mem_search`）。因此来自 engram 声明的注册面是 **20 → 19**；另有 **1** 个插件自有工具 `mem_bridge_recall`，它**沿用 `mcp__engram__` 前缀**，所以带该前缀的工具总数是 **20 → 20**（不变）。验收判据相应写成分离的两句，避免"数不变"被读成自相矛盾：*实册里不再有 `mem_search`、出现 `mem_bridge_recall`；**带 `mcp__engram__` 前缀的工具数保持 20**。*

**连带范围是 9 处，全部在用户侧**（我先前把其中 4 处错标成"仓库内"，实际仓库 `AGENTS.md` 里 `mem_` 出现 0 次——`grep -c "mem_" AGENTS.md` 为空）：

- `~/.dsh/AGENTS.md` 第 26 / 37 / 38 / 43 行，每行一次（共 4 处）。
- `~/.dsh/skills/engram-memory/SKILL.md` 第 8 / 60 / 76 / 77 / 82 行，其中第 60 行同时含"FTS5 全文检索"这一事实错误表述。

两份文件**内容并不相同**（行号与处数都不同），所以**不能**用同一个 grep 验证。这两份文件也**不随插件分发**：插件侧只能保证旧名响亮失败，"模型改叫新名"由用户自己的 skill 决定，因此它是 README 的迁移说明（说明"去哪里改什么"），不是可实现的行为断言，更不该把本机行号写进 README。

### D2 结果如何穿过桥：读层声明自己的规范化值，不伪装成 MCP 结果

宿主契约是每个 `ToolDefinition` 自带一个 `output: { schema, render }`，`render(args, value)` 投影的是"这个工具自己声明的规范化值"。所以分歧不在 render，在 **`execute` 返回什么值**。

选的（b）：读层声明自己的值（`hits` / `shown` / `candidates` / `pool` / `filtered_out` / `timing`），自己的 `output.schema`，自己的 render。被否的（a）：把结果包装成 `{content:[{type:'text',...}]}` 复用 `extractText`——它在三个点上坏：规范化值与渲染结果合体（截断措辞只能拼进字符串）、`output.schema` 变成关于读层的假话、**并且会话日志里与其余 engram 代理工具的结果形状完全相同（来自 engram 声明的代理工具当前 20 个、变更后 19 个，加插件自有工具后前缀集合始终是 20），事后无法判断哪次检索打的是本地派生索引**。最后一点影响的是硬规则 6 所要求的**可重建性与来源可辨认性**（不是"日志里没有这条调用"——调用名本身当然在日志里），也影响本次变更的正当性：既然收窄后的非目标是"不成为第二个真相来源"，那么"派生"这一性质就该在证据里可辨认。

`execute` 也不走 `wiring.run`——它的入参是 `McpToolDeclaration`、实现是 `client.callTool`，读层两样都不是；硬塞要伪造一份声明。实现上拆 `src/recall-tool.ts`（`tools.ts` 已有 `siteOf` 与不注册清单两个可复用件）。

### D3 规范化值与渲染形状

输入：`query`（**单串**）、`limit`、`project`（**声明它是承重的**——注入按 schema 是否声明该键判定）、`all_projects`、`type`、`scope`、`match_mode`（保留并**忽略**，描述里写明）。保留它的理由只是**零成本的兼容**：模型的历史行为里带着这个参数（原生工具声明了它），而读层的词法不是 FTS 的 AND/OR，该参数在这里没有语义。**不**声称"删掉它会让调用被拒绝"——未验证：宿主的参数校验由工具自己的 schema 驱动，而 `json-schema.d.ts` 表明未知键默认是允许的，所以删键大概只是让模型的一次自然调用落空，而不是被拒。

**`injectSessionProject` 关闭时的决定**（这条先前被评审指出"spec 两处要求对撞、design 无决定"）：该开关关闭 ⇒ 不注入 `project` ⇒ "默认只返回当前项目"无从判定。本设计选定：**此时检索被拒绝**，错误说明项目注入已关闭、无法限定项目，并给出两条出路（显式传 `project`，或打开注入）。被否的替代是"以未限定项目运行"——那会让默认隔离在这个配置下静默失效，等于把一条安全要求降级成一个默认值。

每命中字段：`id` / `title` / `type` / `project` / `scope` / `score` / `excerpt`(200 字符)。title/type/project 不是装饰——没有它们模型必须先读全文才能判断相关，而那正是端到端验收里 207→51 的收益来源。

截断措辞约束：`pool` 被 `top_k=50` **硬顶**，在 346 条语料上可能恒为 50，因此渲染**只能表达"还有未显示"，不能说"共 N 条候选"**——后者会被读成语料上限。真正承重的是"看到的条目之外还有没有东西"。

**触顶判定必须继续扫完剩余排序**（评审指出的实现缺口）：参照实现一旦攒够 `limit` 就 `break`（`read.py:397-399`），因此它**分不清**"恰好 limit 条"与"还有更多"。本设计要求在触顶后继续走完剩余排序，只做**匹配判定与计数**、不再做任何内容嵌入，从而精确区分两种情形。代价是一次 O(剩余条目数) 的比较，相对每次调用的嵌入成本可忽略；收益是截断提示不撒谎——这是"截断对模型可见"这条要求能被验收的前提。

不逐条回带 `cosine`/`coverage`/`boost`/`in_pool`（那是参考实现 `--explain` 的诊断量）。**载荷账**：本设计的形状约 260 字符/条 × 10 ≈ 2,600 字符 + 截断行 ≈ **2,740 字符 ≈ 1,712 token**（按 1.600 字符/token 的比例估算；未实测，验收时重测）。

**一处必须说明来源的引用**：讨论中被引用的「参考实现每次调用 6,053 字符 / 3,783 token、检索载荷占检索环节约 88%」是**第三方 agent 的口头转述**。我在本机 `ops/` 下按数值搜过，**没有出处**（命中项都是 sha/hex 或浮点数的偶合子串），所以我**没有**独立复现过这组数字。它由 `HANDOFF.md` 的端到端计数（基线 F 51 次检索对原生 207 次）间接支撑，但那是**调用次数**，不是单次载荷。

因此处置如下：**不把它当物证、不拿它做绝对量决策**。由它支撑的那个**结论**（默认返回条数留 10 而不翻倍）不依赖绝对数——它依赖两条有物证的判断：① P2/P3 都是单金标**查找型**代理，其 R@10 不能用来支持为**聚合型**提高返回条数；② P3 有 93% 的金标本来就在前 5、中位排名 1。载荷本身一律在验收阶段重测（见 tasks 第 7.4 条）。

### D4 进程边界：常驻进程懒启动 + 空闲回收，全量重建走临时高线程进程

**查询路径必须现场嵌入**——参考实现的文档向量是预计算的，查询侧每次都要嵌一次。**增量重索引也要嵌入**：增量设计的立论就是"只嵌变了的文档"，且已验证文档向量与批次无关（批 1/8/32 位相等）。两者共用同一模型会话，所以：

- 常驻进程（懒启动、空闲回收）承担**查询嵌入 + 增量文档嵌入**，1–4 线程（512–572 MB，8.85 ms/次）。
- 全量重建走**临时 16 线程子进程**（约 12 s、峰值 862 MB，用后即退）。

被否的候选：宿主进程内（512–761 MB 常驻落在会话进程里，且 WASM 加载期失败会变成会话失败）；每次调用起停（同一冷启在查询与增量上各付一次，且 668 条冻结查询的 rank 验收要 668 次冷启 ≈ 210 s 对一次加载 ≈ 1 s）。"每次调用起停"**保留为诊断配置档**，不进验收判据。

`numThreads` 必须显式设置（Node 默认取 4）；内存几乎完全由它决定。

**常驻进程的回收参数不复用 engram 连接池的那两个键**——`poolMaxIdleMs` / `poolSweepIntervalMs` 管的是 engram 子进程，把嵌入进程混进去会让一个旋钮同时控制两种毫不相干的资源。改用独立的配置键（暂定 `searchIdleMs` / `searchSweepIntervalMs`），但**沿用既有形状**：由插件自己的定时器驱动、`ctx.effect` 保证卸载清理、在途调用期间不回收。这个仓库已经踩过一次"`sweep()` 是死代码"的坑，新进程必须自带调用者。

### D5 新鲜度：照搬已验证的全量内容哈希，并加计量（本次不优化）

参考实现每次查询用"全部活跃行的 id/updated_at/len/content 求 sha256"与存下的 `source_hash` 比对，不等则增量同步。这条有 V1–V7 背书，本次照搬，**不引入**"先用 `COUNT(*) + MAX(updated_at)` 做廉价闸门"的新假设。

代价是一个**随语料线性增长的每查询成本**（346 条约 346 KB 内容，将来会变贵）。因此加计量：每次调用记 `source_changed`、`rows_scanned`、`hash_ms`、`sync_ms`（0 也记）、`embed_docs`、`total_ms`，并聚合到**周期性摘要**（每 N 次调用或每 N 分钟一行滚动均值）而不是每调用一行 info——既有基线可追，又不膨胀日志。计量落点由 D2 决定：它进读层的规范化值，因此**只有 (b) 才装得下**。

### D6 索引扩列：`docs` 需要 title / content / type / project / scope

参考实现的组织方式是**索引只有词法与计数、正文与元数据来自语料**（`LexicalLayer.fields` 由内存里的 corpus 灌入）；而原型 `liveindex.py` 的 `docs` 表只有 `doc_id/updated_at/content_sha/title_chars/content_chars/n_tokens`，**没有 title、没有 type/project/scope、没有正文**。所以"照搬原型的索引形状"直接走不通：连 D3 的渲染与类型纠错都做不到。

一次性扩列解决三件事：渲染所需的展示副本、筛选判定、以及 D7 的域派生。**它不构成第二个真相来源**的判据：`content_sha` 与 `source_hash` 的比对保证展示副本与正本同事务、同一次同步刷新；副本永远可由正本确定性重算；删除索引即消失。代价是索引多存一份语料正文（346 条约 346 KB，线性增长；对照 109.8 MB 的模型可忽略）。

顺带修正一处**三处重复的常量**：`K1=1.2 / B=0.2 / TITLE_W=3.0 / EVID_W=0.25` 同时存在于 Python 参考（`bigram_lib.py`）、TS 打分器（`scorer.ts`）与索引 `meta` 表（后者的键名是 `scoring_k1` / `scoring_b` / `scoring_title_weight` / `scoring_evidence_weight`）。本次让**索引 meta 成为这些参数的载体**，打分器从它读取，而不是把常量再硬编码进 TS。

**两个来源的优先级要写死，否则又是两个真相源**：
- **索引 meta** 存**建索引时**的计算常量（`scoring_k1` / `scoring_b` / `scoring_title_weight` / `scoring_evidence_weight`）。它们决定**排序**，必须与索引内容同版本——换常量等于换索引，因此由 meta 单方面作准，配置**不**参与、也不暴露这些键。
- **config（Schemastery，硬规则 5）** 只管**每次调用的截取与筛选**参数：`limit`、`top_k`、`coverage`、项目/类型/范围。它们不影响已建索引的内容，改了就只影响下一次调用。

**`w`（覆盖率提升的权重，默认 0.20）归哪一处**——先前没写清，评审指出它被悬空：`w` 不参与建索引（索引里的 `coverage` 是预先算好的），它只在**打分时**用，所以归 **config**（键名 `searchW` 或同类），与 `top_k` / `coverage` 同组；代码里不出现字面量，只有 schema 默认值这一个出处。参照实现里 `w` 恰好只出现在代码常量中，这就是评审对 `tasks` 2.2 那条 grep 的合法反对：`0.20` 会命中 `0.2`——修正后的验收只要求**建索引常量**不出现在代码里，`w` 的默认值则**必须**在 config schema 里出现一次。

扩列改变索引内容，因此 `algo_version` 与逻辑指纹都会变，这是预期（验收判据是"同一算法同一内容跨实现相等"，不是等于旧值）。

### D7 类型不枚举，纠错代替枚举

type 域在**活库**上是 **10 个取值**（取值集合是承重的；**行数会随时间漂移**——冻结快照是 346 条，所以下文的具体计数只作参考）。而 **engram 自己的两份描述不一致，且都不完整**：`mem_save` 列 7 个（`decision/architecture/bugfix/pattern/config/discovery/learning`，另注默认 `manual`），`mem_search` 列另一套 **10** 个（`tool_use/file_change/command/file_read/search/manual/decision/architecture/bugfix/pattern`，其中前 5 个在语料里**一条都没有**）。真实存在而两份描述都缺的至少有三个：`session_summary`、`preference`、`design`；`config` 只被 `mem_save` 列出（约 34 条），`mem_search` 里没有。任何按任一份清单硬编码的枚举都会**拒绝真实存在的条目**并让它们无法被类型过滤到。

因此：不枚举；取值没有匹配项时，结果给出该维度实际存在的取值。域从索引现算（`GROUP BY`，瞬时），**不缓存**——缓存派生值就制造了会陈旧的第二个真相源。

### D8 刻意不做：`since` / `until`、专用"类型列表"工具、hack `mem_stats`

`since` / `until` 按 `updated_at` 过滤，而 `updated_at` 不等于"发生时间"（被更新的旧记忆会跳进时间窗）——模型几乎必然误读成后者；且时间维已有三个更好的入口（`mem_context` 近期、`mem_timeline` 演化、语义检索问"何时定的 X"）。不做，且它是纯增量特性，将来补不付利息。

域分布**不寄生在 engram 的 `mem_stats` 上**：那要在桥侧往 engram 的返回里贴本地数据，一次回答混两个真相源（正本当前计数 vs 索引上次同步快照），engram 升级后还可能同答出现两套分布，而工具描述里无法诚实说明。域分布是人看的运维信息，走日志/诊断。

### D9 派生状态落 `$DSH_HOME/storages/engram-bridge/`，模型与运行时走显式安装

与既有 `tool-cache.ts` 的 `tools.json` 同家（它已确立"插件运行时可重建状态放这里"的先例）。被否的候选是插件目录内 + gitignore：收益是"删插件目录 = 清除全部派生状态"，代价是它同时是 `pnpm link:` 指向的工作副本（`git clean`、换 worktree 会连带清掉），且本机 `web`/`headless` 两个 profile 会共享一份索引、并发重建有争用。路径做成配置项——它同时是跨机验收的必需项（把实现指向冻结语料重建索引）。

**注意本变更牵涉三类位置，别混为一谈**（配置键命名要与之对应，硬规则 5）：① **engram 正本**的位置由**数据库路径**配置给出（桥目前不设 `ENGRAM_DATA_DIR`、也不读该路径，只 spawn engram 让它自己解析——见 HANDOFF 的决定 1，所以读层需要一个**显式**的库路径）；② **派生状态**（索引、向量）落 `$DSH_HOME/storages/engram-bridge/`，路径可配置；③ **模型与运行时**目录独立配置，走显式安装。三者的默认值全部写进 config schema。

**配置键名清单**（frontmatter 的 `anchors.config_keys` 只允许指向这里定义过的名字）：`searchEnabled`（引擎开关）、`searchDbPath`（engram 正本路径）、`searchIndexDir`（派生状态目录）、`searchModelDir`（模型与运行时目录）、`embedThreads`（嵌入线程数，即 `ort.env.wasm.numThreads`）、`searchIdleMs` 与 `searchSweepIntervalMs`（常驻进程空闲回收）、`searchTimeoutMs`（单次调用超时）、`searchW` / `searchTopK` / `searchCoverage`（每次调用的打分与截取参数，归属见 D6）。

**返回条数上限不在此列**：`limit` 是**工具输入**，其默认值（10）只写在工具的输入 schema 里，config 不提供第二个默认——否则同一件事会有两个出处（这正是 D6 要避免的那类问题）。config 提供的是 `searchTopK`（打分加强所及的规模），两者是不同概念，不要混。

**命名撞车要显式处置**：config 里**已有一个** `recallWakeup`，指的是**压缩后召回注入**（`src/config.ts`，配套规格 `engram-compaction-recovery`）——与本变更的"记忆检索"毫不相干。因此新键**除 `embedThreads` 外一律用 `search*` 前缀**（对应工具名 `mem_bridge_recall` 里的"检索"语义），**不沿用 `recall*`**；`embedThreads` 是唯一例外，因为它命名的是**运行时参数**（`ort.env.wasm.numThreads`）而不是检索参数。规格里那句"与压缩恢复无关"就是为这条撞车留的注脚。若将来把压缩恢复整块移除（建议另立变更），这个前缀分歧自然消失。

模型与运行时（109.8 MB）**不进仓库**：门禁对二进制是盲的，且 95 MB 模型是第三方制品。走显式安装步骤，缺失时在调用点响亮失败（缓存为空时会在查询时静默拉 95 MB，而工具调用超时默认 60 s → 新机器第一次检索就撞超时）。

### D10 `onnxruntime-web` 按硬规则 7 的新分层引入

它是第三方依赖，但**纯 WASM、只在子进程内**，不违反那条规则真正要拦的"宿主进程内加载原生代码"。要求：精确锁版本、文档给出安装体积、并有**机制**证明宿主入口没有加载它（一条边界断言测试）。同时它与"裁剪到 14.59 MB"存在张力——标准依赖安装拿到的是 142 MB / 509 文件，所以依赖与"实际发货的运行时"不是同一件东西，安装步骤要能把裁剪后的产物落到模型目录。`node:sqlite` 在 Node ≥22 可用（本机 v26.7.0 实测可用、`loadExtension` 存在、含 FTS3/FTS5），因此不需要原生 SQLite 绑定；这是**在约束下恰好可用**，不是"规则选出了最优解"。

## Risks / Trade-offs

- [**工具面在一次加载内固定**（新增要求，推导在此）：现状 `registerTools` 在首次注册后早返回，只对不同的后续工具面 `log.warn`（`src/index.ts:92-107`）。本变更**沿用**这个既有行为而**不**改成重注册，理由有两条：① 宿主没有提供注销既有工具名的路径，重注册会撞 "already registered"（**这条理由已被实测削弱，见本条目末尾的补注**）；② 重新注册发生在某次工具调用内部，会让工具面在会话中途变化，而模型的 prompt 已经把工具清单编进去了。被否的替代是"发现到不同工具面时注销旧的再注册新的"，代价大于收益。因此"表变了要重启"是**要写进规格的约束**，不是被忽略的缺陷] → 已写入 `engram-bridge-runtime` 的新增要求；`design` 与 `tasks` 都不得再承诺"重启后自动跟上"，缓存指纹只含 `command`/`args` 这一事实也在这条要求里被承认。
  - **实现后补注（被实测推翻的是理由，不是结论）**：5.6 的实测显示配置变更确实会**重建插件条目**，且重建之后生效的检索行为是**新配置**——所以"宿主没有注销路径"这句不足以支撑"只有重载才换工具面"的论证。仍然成立的是那条**要求**本身（一次加载内工具面固定；本变更不改成重注册，另一个理由是重注册发生在某次工具调用内部，会让工具面在会话中途变化）。**未确定的是**：重建时宿主究竟是"注销旧注册再接受新注册"，还是"保留旧注册、而旧闭包读到的是被就地改写的配置对象"——两者的可观察行为本轮一致（新配置生效、且没有出现旧实例被处置后仍服务调用那类症状），区分它们需要读宿主日志或注入探针，本轮**没做**。
- [**Mac / arm64 内存未测**：常驻内存随 WASM 堆与 worker 开销变化，而 512 MB（1 线程）是一台 Linux x86-64 机器上的读数] → 上线前在目标机器上重跑一次内存剖析（`<spike>/wasmspike/mem_profile.ts`，**仓库外物证**），判据 **1 线程稳态 ≤ 600 MB**；超了就降线程或重新评估 TS-only 路线。这是唯一可能推翻本路线设计的测量，其余未验项都是加固性质。**落点见 tasks 第 7.5 条**——review 指出这条原先只写在 design 里、没有任何任务承接。
- [**指纹类验收有自证陷阱**：扩列后逻辑指纹必然与旧值不同，"记录新值再复现"只证明确定性、不证明移植正确] → 验收不靠自比：对冻结语料做**词法表逐行比对**（V5 已有 346 文档 / 28181 词项 / 79157 posting / 13 meta 逐行相等的先例），指纹只作为"同一内容跨实现相等"的辅助判据。落点见 tasks 第 7.1 与 7.2 条。
- [**大积压未验**：桥停数日后增量可能是上千行，低线程档下同步可能吃掉数十秒，而它发生在一个正在等结果的回合里] → 这是**已知未验**：本次**不**设计积压上限策略（那也是 Open Questions 里的一条），只在实现里对单次调用的同步工作量设一个显式上限：超过就提示"索引落后较多"并建议重建，而不是让调用无限期地同步下去。验收不覆盖大积压，如实标注。
- [**每查询全表扫的计量会偏乐观**：小语料下内容几乎总在页缓存里] → 计量报告必须同时记语料规模，并把"线性增长的每查询成本"写进已知风险，避免将来拿小语料读数做决策。
- [**带筛选的检索质量无代理集**：V6 只证明了"不破坏已验证排序"] → 保持后置筛选，不为它调参；需要它自己的代理集才谈优化。
- [**合并双向量无留出确认**] → 保持 opt-in、默认关。
- [**`w = 0.20` 与排序参数不得随手调**：它是 P2 调参、P3 留出确认的] → 每个参数只有**一处**作准（建索引常量归索引 meta，调用参数归 config，见 D6），诊断性取值不参与验收。
- [**干净深度 23 是回归参数不是产品限制**：depth 24 起有 1/668 分歧，来源是 float32 累加顺序] → 写进验收判据的边界说明，不当 bug 修。
- [**模型可能继续调用已消失的 `mem_search`**：用户侧 skill 不随插件分发] → 保证旧名以未知工具错误响亮失败 + README 迁移说明 + 同步修订本机两份用户侧文件。
- [**常驻子进程需要自主回收**：本仓库已发生过"`sweep()` 无调用者"的死代码事故] → 回收由插件定时器驱动并用 `ctx.effect` 保证卸载时清理，验收含"卸载后无残留子进程"。
- [**内存预算与线程数耦合**：内存几乎完全由 `numThreads` 决定] → `numThreads` 显式配置并在文档中标注它与内存的对应关系；长驻路径默认低线程。
- [**首次安装的体积与静默下载**] → 显式安装步骤 + 缺失时响亮失败（已列入验收信号）。

3. 用户侧（本机）：更新 `~/.dsh/AGENTS.md`（4 处）与 `engram-memory` skill（5 处）里合计 **9 行 / 9 次** 工具名，并补上"省略范围时两种范围都返回"（原生描述里那句 "project (default)" 是错的）。
4. 索引：首次运行由显式安装步骤建立（或首次检索时自动重建）；`algo_version` 与逻辑指纹会因扩列而改变。
5. 回滚：关闭引擎开关即退回（调用点在开关关闭时以明确原因拒绝检索）。**已在活宿主实测（tasks 5.6/8.5）：开关改动即时生效，宿主进程不需要重启。** 观测到的机制是宿主在配置变更时**重建该插件条目**（`cordis-plugin-loader` 的 `Entry.update` 语义 "Merge new options, restart as needed"）：两次改动 `~/.dsh/cordis.patch.yml` 各触发一次 `apply()`（`tools.json` 被 discovery 重写于 <时刻> 与 <时刻>），而 dsh 宿主进程（pid 省略，启动 <时刻>）**始终没变**；改后紧接着的调用即按新值行为，撤销后恢复。删除索引目录即回到"无派生状态"，正本不受影响。
