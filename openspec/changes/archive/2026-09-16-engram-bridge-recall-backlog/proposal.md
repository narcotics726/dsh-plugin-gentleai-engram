## Why

读层在检索调用内更新派生索引，而单次调用有预算。变化量超出该预算时，检索既做不完也不报错：它在同一步被杀，下一次调用从零重来——活锁。变化量由**滞后时间**而非语料规模决定，所以离线一段时间的机器、或别的 agent 在写而本机没检索，都会撞上。同一根悬崖还有两处：上限按「是否增量」执行，而不是按「要做多少工作」；「索引不可信」被当成特例，绕过一切上限。

## What Changes

- 判定只按**工作量**：Δ 在常驻自动限额内 → 自动做完（增量与全量走同一条路）；超出 → **以明确原因拒绝**，并指出一个**显式入口**（工具）。
- 大的积压不再由常规检索静默承担：等待变成调用方的显式选择；拒绝文本给出待处理条数与预估秒数。**自动转交与重试一次消失**，「索引不可信」就是 Δ = 全量。
- 第三种情况（连显式入口单次也放不下）有一条**操作者直接发起**的路径：在会话里敲一条命令，跑到完为止——不改配置、不重启、可取消。
- 同一份派生数据同时只允许**一次更新在进行**；并发的多次触发不会让派生数据出现半成品或倒退，更新中断（含被强制终止）之后不需要人工清理。
- `MAX_INLINE_SYNC_DOCS` 与 `mode === 'incremental'` 这个判定条件一起消失；常驻内存不变。

## Capabilities

### New Capabilities

（无：这是既有能力内部的判定、失败路径与并发语义，不引入新的对外能力。）

### Modified Capabilities

- `engram-bridge-recall`: 「内容变化对下一次检索可见」补上自动限额的边界（并写明并发更新在进行时该次调用可以「正在更新」失败）；「派生索引与当前声明的模型同代」「检索不改变记忆且结果可重建」「运行时或模型缺失时响亮失败」（其中的「派生数据损坏」一档）都改走同一条工作量判定；「派生数据的更新是原子的」补上并发读的边界（可以明确失败，不得返回半成品）；「引擎开关在调用点生效」扩到同样约束显式入口；新增「超出自动限额的工作以明确原因拒绝并指出显式入口」「并发触发时同一份派生数据只有一次更新在进行」与「超出单次预算的更新可由操作者直接完成」。

## 验收信号（可观察）

| 信号 | 观察方式 |
|---|---|
| 小积压自动 | Δ 在自动限额内：紧接着的下一次检索直接看到变化；派生数据被删而语料很小时，同一次检索自恢复 |
| 超限即拒绝 | Δ 超出自动限额：该次检索以明确原因失败，错误给出待处理条数、预估秒数与可用的显式入口；派生数据逐行未变 |
| 显式入口能做完 | 按该入口同步一次后，同一查询成功并看到全部变化；**不改配置、不重启宿主** |
| 连长预算也不够 | 工作量超出显式入口单次上限时，该入口当场拒绝、指出规模，**并指出由操作者直接发起的那条更新请求**，而不是开始一次会被中断的重建 |
| 操作者请求可直接完成 | 在会话里发起那条更新请求后，紧接着的检索看到全部变化；不改配置、不重启宿主、可取消 |
| 该请求运行期间 | 并发的检索拿到「正在更新」拒绝而不是半成品 |
| 并发只有一次更新 | 两个触发并行（含两次操作者请求、检索与显式入口同时）时，派生数据不出现半成品、不倒退；未获准的那个要么在它完成之后基于最新内容继续并返回结果，要么拿到明确的「正在更新」拒绝 |
| 更新中断后可恢复 | 一次更新被强制终止后，紧接着的下一次触发能接管（若工作量超出自动限额，则以该原因拒绝并指出显式入口），不需要人工清理 |
| 原子性不变 | 拒绝、失败与中断之后，派生数据与上一次成功更新后逐行一致；**原本就缺失或不可读时除外**——那时它只需保持不能被用来作答、且紧接着的下一次触发能自行重建它 |
| 开关约束模型入口 | `searchEnabled=false` 时调用显式入口以同一原因被拒绝，且不加载模型、不写派生数据（操作者那条不受约束） |
| 常驻内存不变 | 常驻仍按 `embedThreads` 起；高线程只出现在显式入口触发的短命进程里 |

## Impact

- 代码：`src/recall/index-db.ts`（`maxDocs` 与 `deferred`，删除 `MAX_INLINE_SYNC_DOCS`/`BacklogError`）、新增 `src/recall/index-lock.ts`、`src/recall/engine.ts`（统一的判定与限额内全量重建）、`src/recall/process.ts`（自动限额、拒绝、一次性进程、常驻静默、退出码归一）、`src/recall/worker.ts`（一次性模式 `--rebuild` 强制全量 / `--sync` 追上，两者同受限额与锁）、`src/recall/protocol.ts`、新增工具定义与其在 `src/index.ts` 的注册、**新增人类命令的注册（`inject` 加 `commands`，开发依赖加 `@deepseek-ai/dsh-commands`）**；`src/config.ts` 不新增键。
- 脚本：`scripts/mem-profile.mjs`（一次性进程的 RSS 采样路径）、`scripts/check-recall-boundary.mjs`（把锁模块列进宿主入口的禁触清单，让"锁只在子进程里"成为机制）。
- 测试：`recall-index`（上限成为机制参数）、新增锁的并发/陈旧/接管用例、`recall-process` + stub（拒绝、显式入口、正在更新）、`recall-engine`（限额内全量重建）、`recall-wiring`（工具面计数，以及"工具声明为空时命令仍注册"）、命令的注册/取消/无上限用例。
- 文档：`README.md`（新工具与 `searchTimeoutMs` 的语义，以及那条操作者命令的用法、可取消、不受引擎开关约束）；`design.md` 记录速率读数、锁协议、并发语义与操作者路径；以及两处**用户侧文件**（`~/.dsh/AGENTS.md`、`~/.dsh/skills/engram-memory/SKILL.md`）需要补一句"拒绝 → 调显式入口 → 重发检索"，插件只能保证工具与文案存在。
- 成本：模型工具面 +1（每个请求都携带）；显式入口会占住一次调用的墙钟；并发时同时只有一个高线程进程（这正是锁要保住的）。
