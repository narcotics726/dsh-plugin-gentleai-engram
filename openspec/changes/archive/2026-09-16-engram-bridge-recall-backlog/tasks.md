## 1. 锁：同一份派生数据只有一个写入者

- [x] 1.1 新增 `src/recall/index-lock.ts`：实现 `design.md` D6 的协议。具名常量：`STALE_WINDOW_MS`（拟 5 min）、`STALE_MARGIN_MS`（拟 30 s）、`LOCK_WAIT_AUTO_MS`（2 s）、`LOCK_WAIT_OPERATOR_MS`（5 s）。要点：`wx` 建 + 写**完整记录** + **保留 fd 到释放**（心跳要用它）；拿到锁的判据是**按路径**重读 token（读回只用于判定）；陈旧判定的三条钟表/进程判据**都只在 `host` 一致时生效**（同机 pid 不存活 → 快速接管；`now - lastProgressAt > WINDOW + MARGIN`；`now < lastProgressAt - ε`），另有"读不出且比 ~2 s 更老"；陈旧只能原子 `rename` 偷；按 token 释放并**关闭心跳 fd**；`heartbeat()` 走创建时的 fd：`ftruncate(fd,0)` → **`write(fd, json, 0)`（必须显式写位置 0——`ftruncate` 不重置偏移，否则文件会变成 `"\0…" + JSON` 而永久不可解析）** → `ftruncate(fd, byteLength)`，写完**按路径读回自检**（`JSON.parse` + token + `(dev,ino)`），不符即放弃本次写入；向外提供写事务内的复核（**按路径 `stat`**，不能 `fstat(fd)`——fd 永远匹配自己）；200 ms 轮询 + 调用方给的等待窗口。
  - 验证：单测覆盖（a）两个并发获取只有一个成功；（b）持有者写一个不存在的 pid → 接管；（c）pid 存活且记录很新 → 不接管，等待窗口耗尽后以「正在更新」失败；（d）token 不匹配时不删别人的锁；（e）内容为空/半截且很新 → 不判陈旧；（f）pid 存活但记录已超窗口 + 余量 → 按陈旧接管；（g）记录时间在未来**且 host 一致** → 接管；**host 不一致时不得**因钟表判陈旧；（h）获取后把锁文件删掉/替换成别人的 token → 复核失败（用 `fstat(fd)` 的写法必须**不能**通过这条）；（i）**`heartbeat()` 之后按路径读出的内容仍能 `JSON.parse`、token 仍是自己的、`(dev, ino)` 不变**（这条同时钉住"写位置 0"）；（j）恰好超窗口但在余量内 → 不接管；（k）持续心跳的持有者跨过多个窗口仍不被接管；（l）释放后心跳 fd 已关闭。
- [x] 1.2 写入者必须**持锁后重读正本**，并且**丢掉引擎缓存的索引句柄**：常驻与一次性子进程都改成「先拿锁 → `close()` 并置空 `this.index`/`this.scorer` → `readSourceState` → diff → 比限额 → 嵌入 → 提交」；锁外的预检读只是咨询性的，不得作为写入依据；计量里的 `hashMs` 记锁内那次。
  - 验证：单测构造「锁外读到旧快照 + 索引句柄已被缓存 + 锁内正本已更新」的组合，断言落盘后的 `source_hash` 等于**锁内那次**读到的新快照、且索引不倒退。**这条场景在常驻 `query()` 里复现不了**（常驻没有理由做锁外预读），所以用 `syncOnce(policy)`（3.3 本来就有锁外短读）覆盖，或给引擎加一个与 `onEmbedLoad?` 同形的测试接缝（`onBeforeLock?`）。
- [x] 1.3 三条路径的锁等待策略不同：自动 2 s、一次性按自身预算的大半、操作者固定 5 s；等待窗口由调用方传入（随 `childEnv` 下传，见 4.3）。
  - 验证：单测分别断言：自动与操作者在锁被长持时**很快**返回「正在更新」（断言**耗时上界**，例如 < 10 s——只看错误 kind 会把 60 s 的 `busy_timeout` 路径也放过），一次性则继续等并在锁释放后完成。

## 3. 引擎：统一判定与限额内重建（`src/recall/engine.ts`）

- [x] 3.1 **限额内由常驻重建，顺序钉死（与 1.2 一致）**：拿锁 → 立刻 `close()` + 置空（丢掉 `ensureIndex()` 缓存的句柄）→ 锁内 `readSourceState` + 重新 inspect → 算 Δ（不可信时 Δ = 全量）→ 比 `maxDocs` → **只有不超限才做就地全量同步**（`sync({full:true})`：一个事务里清空 + 重写全部行 + 改 meta；**不用 `IndexDb.recreate`**——它是 unlink 三个文件再单独提交一个空索引，与随后的同步不在同一事务里，中间被 SIGKILL 就留下"空而有效"的索引，且大语料下没人能自动恢复）；超限则抛转交判定（`mode: 'full'`），**索引一个字节都不动**。`recreate` 只留给"文件缺失/不可读/`integrity_check` 失败"。这是 D5，也是"无数据 = Δ 全量"这条统一模型的落点。
  - 验证：`test/recall-engine.test.ts` 新增——（a）语料 1 条、**索引文件被删**、`maxDocs = 10` → 同一次 `query()` 自恢复并返回结果；（b）语料 1 条、**索引被写成垃圾**、`maxDocs = 10` → 同样自恢复（两个分支都要覆盖）；（c）同样夹具但 `maxDocs = 0` → 抛 `mode: 'full'` 且 `pendingDocs` = 语料条数，**且 `storedHash()` 与失败前相同**（拒绝不得清空索引）；（d）就地全量同步的中断：沿用既有 `SIGKILL` 手法在写事务中途强杀，断言索引仍等于上一次成功状态（不再存在"先提交一个空索引"的窗口）。
- [x] 3.2 新增 `SyncNeededError`（带 `mode: 'incremental' | 'full'` 与 `pendingDocs`，`kind = 'sync-needed'`）；`query(request, policy: { maxDocs?: number, waitMs?: number })` 把 `sync()` 的 `deferred` 与超限的重建统一成它；`engine.rebuild(policy)` 同样受限额约束（超限抛同一个判定），且 **`policy` 必填**（类型层面不给缺省——D2 说机制的缺省只给测试夹具用，否则那句就是宣言而不是机制）。
  - 验证：**两种 policy 必须分开命名**（`SETUP_POLICY` 允许全量建库、`DENY_POLICY = { maxDocs: 0 }` 强制拒绝），因为同一条 `query()` 在 `maxDocs ≥ 语料条数` 时走的是 D5 的自重建分支、**根本不会抛**。据此：（a）既有「换代后整体重建」「派生索引损坏」「向量数不一致」三条的语料都只有 1–2 条，改成断言**同一次 `query()` 自重建并返回结果**（普通 policy），即"不再需要外部重建"；（b）用 `DENY_POLICY` 在同一批夹具上断言 `kind === 'sync-needed'`、`mode === 'full'`、`pendingDocs` 等于语料条数，且 `storedHash()` 未变；（c）**限额内的大变化**——`maxDocs = 45` 而语料 40 条、全部是变化 → 同一次 `query()` 返回全部变化、`metering.mode !== 'deferred'`；（d）**重复拒绝不是活锁**——`DENY_POLICY` 下连续 `query()` 两次，两次都抛同一个 `sync-needed` 且索引逐行不变。
- [x] 3.3 新增 `syncOnce(policy)`：一次性入口用。顺序必须是「短读预检（锁外，仅用于决定走哪条路）→ 拿锁 → **锁内重读正本** → 重算差异 → 比限额 → 才加载模型」；超限时释放锁并抛转交判定，且**不加载模型**。
  - 验证：单测用一个"加载即抛错"的嵌入器夹具，断言超限时返回的是超限判定而不是加载错误（证明限额判定在模型加载之前）；限额足够时正常完成，且逐行等于全量重建。
