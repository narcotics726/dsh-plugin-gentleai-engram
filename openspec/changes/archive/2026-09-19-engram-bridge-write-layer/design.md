### 上游候选机制的机制事实（读 v1.20.0 源码所得）

- `FindCandidates` 只拿**标题**构造 FTS 查询（`sanitizeFTSCandidates(title)`），`observations_fts MATCH` 的建表未指定 tokenizer（默认 `unicode61`）。
- BM25 权重是 `bm25(observations_fts, 5.0, 1.0, 0.0, 0.0, 0.0, 3.0)`：title 5.0 / content 1.0 / topic_key 3.0，另三列为 0。默认地板 `-2.0`，默认条数 3。
- 每个候选**无条件**插一行 `pending` 关系行；`mem_save` 的 handler 里没有开关，`MCPConfig.BM25Floor` 这类覆盖字段在 1.20.0 里**没有 CLI/env 入口**（`cmd/` 全部 Go 文件无赋值；二进制里没有 `bm25-floor` 串；22 个 `ENGRAM_*` 里没有 BM25）——这条把「不换通道也能关掉候选」的备选判死。
- 现场读数（本变更动工前）：一次保存返回 3 个候选，得分 ≈ `-2e-6`（贴着地板那一端），且它们靠标题里的 ASCII（`engram-bridge-p0` / `1.20.0` / `tool_name`）命中，中文没有参与。这 3 行 `pending` 就是这么来的。

### 上游 HTTP 面（v1.20.0 路由表）

- 写入 `POST /observations`（body 解成 `AddObservationParams`：`session_id` / `type` / `title` / `content` / `tool_name` / `project` / `scope` / `topic_key`）；会话、检索、统计、冲突（`scan` / `judge` / `compare` / `deferred/replay`）各有对应路由。
- `ENGRAM_HTTP_TOKEN` 只包 6 条路由（删除类、导出/导入、项目迁移），**`POST /observations` 与 `POST /conflicts/judge` 未被包**。使用者已裁定：本机暴露面属额外增强，本次不处理。
- `/health` 自报 `version: 0.1.0`（不是 engram 版本）⇒ 只能判可达性，**不能作版本特征检测**。
- 关系动词：`JudgeBySemantic`（= `compare`）对 `not_conflict` 直接早退、存在性检查是双向的，所以同对重复下判是**改写**、连别的路径留下的 `pending` 行也能顶掉；`JudgeRelation`（= `judge`）只按 `sync_id` 查存在、**不要求该行处于 pending**，而 `compare` 的返回值里就带着刚写下那条关系的 `sync_id` ⇒ **同回合内两步撤销可达**（我先前写「入口不可达」是错的，见 D7）。仍然不可达的只有**旧的、别处写下的**关系：没有任何工具列出关系行并给出它们的标识（`mem_context` 会渲染关系，但不给标识）。
- `mem_save` 的 MCP 入参里**没有** `tool_name`；而 `AddObservation` 会把 `params.ToolName` 写进 `observations.tool_name`，该列同时是 FTS 的列之一、BM25 权重 0.0（不影响排序）。

### 派生读层的可用件（复算所得）

- `readSourceState` 的整表内容哈希实测 **8.3 ms**（563 行 / 796k 字符）；`count(*)`+`max(id)`+`max(updated_at)` 的廉价代理 **0.14 ms**。`RecallMetering` 里已经有 `sourceChanged` 这个字段，语义就是「本次调用时正本与索引快照不一致」。

- 派生索引是 WAL + `BEGIN IMMEDIATE` **原地**事务，没有 temp+rename ⇒ 只读打开看到的一定是已提交状态。

## Goals / Non-Goals

**Goals:**

- 保存这条路上不再产生无效候选与它们的 `pending` 行。
- 保存时给模型**真的**候选：由已有派生数据算出，带足以裁决的机械证据。
- 写入本身不因候选、派生数据、运行时或模型不可用而失败。
- 裁决落进 engram 自身的关系记录，插件不另存一份真相。
- 与既有读层共用同一套「相似」定义，而不是在同一个会话里给出两套。

**Non-Goals:**

- **读层认判决**（被取代的降级/排除）——单独一个变更。理由：它要动读层最稳的那部分契约（得分不受筛选影响、截断只由匹配项决定），不该由「换一根写入管子」来背这个风险。
- 把 `pending` 的概念搬回来：候选不落库、不跨回合、不补发。
- 关闭写入面的本机暴露（使用者裁定为额外增强）。
- 与上游 v2 赛跑：按在用基线 engram 1.20.0 做。trigram 分词对**比重最大的中文二字词**收益有限（<3 rune 的查询会走有界 LIKE 扫描），且 v2 仍是 prerelease。
- 候选**召回率**的研究（理由见 D9）。

## Decisions

### D1 换保存通道：走 HTTP 写入面，上游写入工具不再注册

| 备选 | 否掉的理由 |
|---|---|
| 用 `MCPConfig.BM25Floor=0.0` 静默关掉上游候选，保留 `mem_save` | **死路**：该字段无 CLI/env 入口（见 Context）；上游自己的测试断言 0.0 时零候选，所以它能用、只是够不着 |
| 保留 `mem_save`，在桥内后处理它的结果、追加我们的候选 | 上游候选与 `pending` 行照旧产生（真库 13 行 + 一次保存 3 行的现场读数）；而「入口产生的垃圾在出口过滤」正是读层已经判定无效的形状 |
| 新增一条不扫描候选的写入口（**本次选择**） | 上游本来就有一条：`POST /observations` 与 MCP `mem_save` 共用 store 层（FTS 触发器 / 去重 / `topic_key` 升版 / `review_after` / 同步入队 / session 归属逐项一致，已在隔离库核对过），差别只在候选扫描与 prompt 捕获 |

**真正的归一化必须由桥在两条路径之前统一做**（复核抓出的一个会让幂等性失效的细节）：上游 MCP 的保存 handler 会把缺省的 `type` 补成 `manual`、把 `observation` 映射到 `content`，而 HTTP 写入面**不做**这两件事；两边的去重条件又包含 `type`。于是同一个调用在两条路径上会写出**不同内容**，超时回退就会落成两行。所以：缺省值与别名映射是**桥的职责**，两条路径发出的内容 SHALL 逐字相同。

代价照实写：走 HTTP 就丢掉 MCP 信封里的 `state` / `review_after` / suggested `topic_key`，也丢掉 ambiguous-project 恢复流程（桥自己有项目解析）。这些都不进模型可见结果。

**环境前提（复核抓出，会影响默认机器上的行为）**：HTTP 写入面只在 `engram serve` 运行时存在；插件的默认配置是 `args: ['mcp']`（只起 stdio），所以**不跑 serve 的机器上新路径会 100% 走回退**。裁定：这是**安装前提**，插件不负责发现或启动它（该进程同时承载云同步，不该由插件代管）；README 与升级清单要写明，验收信号里「不新增待判行」那条限定为**写入面可用时**。

### D2 候选排序复用读层自己的打分；词法两数降级为「证据」

一度主张「纯词法池」（宿主侧读 postings，不碰 worker 与模型）。**使用者推翻，理由成立**：索引与模型已经在了，不用是浪费；更要紧的是**一致性**——同一会话里检索已经给模型看过一套「相似」，保存时若换另一套排序，就是两套定义并存。

第一轮我把这条「一致性」实现成了「余弦拿池 + 另一套词法分重排」。**读数否掉了那套重排**（见文末读数第 5–7 条）：它**完全忽略余弦名次**，池越大越容易被「词面相似、语义无关」的 hub 文档顶掉真伙伴（K 30→100：池命中率 39.2%→63.2%，而展示 R@5 反而 .176→.160）。

**但「直接复用读层打分」并没有在展示精度上赢过它**——第三轮做了配对比较（McNemar）：两条管线在 R@1/R@3/R@5/R@8 上每一个 M 的差都 ≤2.4pp，而噪声 σ 是 2.4–3.1pp，**不可区分**。c2 唯一稳定的优势是**池命中率更高**（K=30 时 +4pp、K=100 时 +2.4pp）。所以选择读层打分是**工程理由**，不是读数理由：

1. **只有一套打分**：它已经在跑、已经对检索验证过，写层复用即可，不必维护第二套排序（而第一轮那套的模板惩罚在本样本上还是不可测的空操作）。
2. **样本在向量占优的地方是瞎的**：样本取自上游 FTS 按标题**已经找到**的对，天然偏向「词面可达」。换句话说，这个读数**看不到**「换一种说法、词面不重叠」的那类近重复——而那正是只有向量那一半能救的区域。用 c2 是在补这个盲区。
3. **一致性**：候选就是「这段文本在检索里的前几条」，与模型刚看过的完全同源。

连带三件事：

- **两个词法数（共享稀有 token 的 IDF 和、模板惩罚）从排序信号降级为「证据」**——这与笔记自己的裁定同形（结构相等不作权重、作证据呈现）。判据是实测：把它们当**唯一**排序输给读层的混合分；而附1 的 AUC 0.757 是「已被机制捞出的对」上的**二分类判别力**，不是**全库排序力**，两者不矛盾、但不能互推。
- **boost 池 B 是真旋钮（我先前说「K 只是上限」是错的，那是上一轮一处呈现缺陷造成的错觉）**：B=30 与 B=100 对 125 个查询给出**完全不同的全序**（top-8 仅 18/125 相同），因为查询的词法候选几乎覆盖全库（平均 561.9/562），截断位置决定谁拿到覆盖加成。它有**浅最优**：R@3/R@5/R@8/R@20 在 **B≈20–30** 见顶，B 再大只买池命中、损失展示精度；约束是 **B ≥ M**。
- 排序与池都在常驻进程内做（向量 / postings / df 都在派生索引里；宿主不该读它做打分）。这也否掉了「宿主复用检索命令拿池 + 宿主侧重排」的混合形状。

**两条旋钮要分开配**：**B**（覆盖加成的池）**复用读层检索自己的那个默认值，不自立新键**——实测最优点在 20–30，而检索的默认值在噪声内（R@5 差 1 对），为这点差别多一个键不值；**M**（**展示条数**——真正决定模型注意力成本的那个数，初值 5）是**新的配置键**。数值的原始出处都在 config schema 的默认值里，本规格不重述。

### D3 候选在写入之前算，并把「本次将更新谁」当成一个契约分支

三条理由：(a) 不必让派生数据为**我们刚写的那一行**追新；(b) 免掉自排除（否则新行以满分出现在自己的候选里）；(c) 若是 `topic_key` 升版或内容去重命中，池里天然会有**那条正在被更新的既有版本**——那是证据，不是噪声。

**(c) 是复核抓出来的一处硬矛盾，值得记下**：我原先在 spec 里写「候选 SHALL NOT 包含本次刚写入的那一条自身」，而 D3(c) 又要那条被更新的旧版本出现——**升版/去重命中时这两者是同一行**（engram 命中 `topic_key` 或规范化内容去重就 UPDATE 同一 id 并返回它）。改法是把这个分支写进契约：**候选集是「写入前的既有记忆」**，因此天然不含「本次将新建的行」（写入前它不存在）；若本次写入将**更新**某条既有记忆，**且那一条出现在候选集里**（候选是有限的展示，派生数据也可能落后），它 SHALL 被标明「本次将更新它」；不在候选集里则不承诺出现。
**这个标注不需要预判**（二审确认）：后端在两种命中下返回的都是**既有行的标识**，而新建行的标识必然大于写入前已存在的所有标识，所以「返回的标识落不落在写前候选集里」是**不会误报**的写后判据——实现就是拿响应里的标识比一遍再打标。附带两条防御：对（pair）路径的两个标识 SHALL NOT 相同（上游对 `source_id == target_id` 没有自反保护）；升版/去重那一支里「本次落库标识」与被标候选是同一个标识，因此那一支**不构成可写的关系对**。

### D4 候选查询是一条新契约：按当前派生状态作答，不追新

与检索契约的边界，逐条写清（这些是**刻意相反**，不是疏漏）：

| | 检索 | 候选查询 |
|---|---|---|
| 追新 | 必须（「变化对下一次检索可见」） | 不追；只读当时已有的派生状态 |
| 派生数据缺失/不可信 | 触发重建，超限则以明确原因拒绝并指出显式入口 | 只表现为「本次没有候选」，**永不触发重建** |
| 运行时或模型缺失 | 在调用点**响亮失败** | 静默降级为无候选 |
| 单次预算 | `searchTimeoutMs`（默认 60 s） | 独立的短预算（见 D5） |

它不会长成「第二条同步政策」：它**永不同步**。

### D5 短预算 + 静默降级；写入永不因候选失败

保存是核心能力，候选是增强。因此：候选有独立预算；超时/失败/运行时缺失一律降级为「本次没有候选」；写入的结算不与候选绑定，也不等待它超过自己的预算。上游同形（候选在事务后算、错误吞掉、失败保存），这里保持一致。

冷进程是真实的代价：一次会话里第一次算候选可能撞上模型加载。由短预算截断 ⇒ 表现为「这一次保存没有候选」，不表现为卡住或失败。

### D6 候选不落库、当回合过期

「过期作废」是使用者裁定：不把 `pending` 搬回来。**二审指出我在这里的措辞与仪表放行相抵，已收窄为**：插件不为候选保留**持久**状态、也不把候选喂给后续调用（不重发、不恢复、不补发、不影响后续调用的排序）；**允许**的是会话内的内存计数（不落盘、重启即失、不参与行为）。两个后果要写进协议文本：(a) 候选只在那一次保存的结果里有效——不写，模型会以为可以稍后裁决，然后静默丢失；(b) 漏掉的候选不补发，**下一次保存重新算池就是重试路径**，不需要状态。

### D7 裁决走对（pair）路径；撤销在同回合内两步可达

- **记录 / 改写**：对两个条目标识下判即可，走 engram 的关系写入路径。它的存在性检查是双向的 ⇒ 同对重复下判是改写，不是新增；连别的路径留下的 `pending` 行也能被它顶成 judged。所以**不需要新造一个「类 judge」的工具**。
- **方向**：这条路径把第一个参数当 source、第二个当 target，`取代` 的语义就是「source 取代 target」。**材料先前通篇没写这个约定**（复核抓出）。定为：**第一个 = 本次保存落库的那一条，第二个 = 候选**，因此结果里必须同时给出两个标识（见 D12 与 save spec）。
- **「无关」是空结果，不是一条关系**：这条路径对 `not_conflict` 直接早退、不写任何行（连改写都不做）。所以协议与 spec 都要写明：「无关」不产生记录，且这是**正常的空结果**；而经验上它恰恰是最常见的结果。
- **撤销**：**我先前判它「有动词、无入口」，这是错的**（复核证伪）。对路径的返回值里就带着刚写下那条关系的 `sync_id`，而关系裁决动词只按 `sync_id` 查存在、**不要求该行处于 pending**。于是同回合内 `写成关系 → 用它的 sync_id 判 not_conflict` 就是一条**可达的两步撤销**。真正不可达的只有**旧的、别处写下的**关系：没有任何工具能列出关系行并给出它们的 `sync_id`（`mem_context` 会渲染关系，但不给标识）。⇒ 协议要教「同回合撤销」这两步；D10 里那个「读层要不要露出关系行标识」的问题也随之收窄为**旧关系**的撤销。
- 代价：走对路径写下的关系，其归属字段由 engram 的既有语义决定（`engram` / `system`、会话列为空），插件不补。
- 风险（比先前小）：误记「取代」可在同回合内两步撤回；**跨回合**才需要人工介入。缓解仍是协议里那条「取代/冲突 + 架构或决定类 ⇒ 在同一次回复里问使用者并把编号写进问题」。

### D8 留痕：写入标记落在来源列；`NULL` 即「不是 HTTP 路径」

HTTP body 收 `tool_name`，MCP 的保存工具入参里没有它 ⇒ **只有 HTTP 路径能盖这个标记**。但「哪条路写的」**不能只靠它判定**：请求根本没到达服务（连接被拒）或服务端回滚时标记必然缺席；响应超时那条路可能已经提交，于是那一行带着标记却仍走了回退。判据是结果文本 + 日志，标记只是必要不充分的旁证（详见 D8 后半段）。

边界照实写：`NULL` 只说明「不是本插件的 HTTP 路径」，**区分不了「我们的回退」与「别的客户端写的行」**（两者都空）。所以回退这件事仍由日志 + 保存结果文本承担，两者各留一条可归因记录。标记串定义为常量且不再改（改名会把审计史劈成两段）。

**这个标记是模型可见的**（复核指出）：`mem_get_observation` 会渲染「Tool: &lt;tool_name&gt;」，而协议恰恰要求模型在下判前读候选全文；这一列本来也已被被动捕获写成 `dsh-turn-stopping`。所以它不是隐私通道，只是一个来源事实——照实保留，并在 design 里记明。

**标记不是回退的充分证据（二审修正）**：`tool_name` 只在**请求根本没到达服务**（连接被拒）或服务端出错回滚时必然缺席；**响应超时**那条路可能已经提交，于是那一行带着标记却仍走了回退（去重命中分支只更新 `duplicate_count` / `last_seen_at` / `updated_at`，不碰该列）。所以判据是**结果文本 + 日志**，标记只是「走过写入面」的必要不充分证据。验收里那条「标记为空 ⇒ 可判回退」用**连接被拒**构造，才成立。

### D9 待观察判据（仪表，不承担行为）

**仪表可以有会话级的内存计数**（进程内、不持久化、重启即失、不参与任何行为）。**二审指出我第一版的辩解站不住**：D9.4 要跨回合把「本会话被检索过的标识」与候选池对照、D9.5 要把候选标识留到判决时，那确实就是同一批标识被留到后续回合。所以契约要**分两句写**（spec 已改）：**行为性**的 SHALL NOT 只管「不重发 / 不恢复 / 不补发 / 不影响后续调用」；**允许性**的一句放行会话内内存计数。D6 那句话也随之收窄为「不为候选保留**持久**状态、也不把候选喂给后续调用」。池组成按**每次调用**记录即可，出现率由日志外推。

1. **落后**：复用 `sourceChanged`——它本来就算、本来就在计量里返回，语义与读层完全同一个。候选查询不追新，因此要沿用同一个整表内容哈希来填这个字段。**判据**：若「落后」在保存里的占比高（例如 >20%）或中位落后规模大（例如 >10 条），说明「不追新」在真的丢召回，届时两条出路——候选查询内做**有界**追新，或只对「缺在索引里的那几条」做宿主侧词法补捞（`tokenize` 零 import，缺的条数就是落后的规模，天然有界）。**退役**：判据落地即删。它是仪表，不是遥测；且日志落点走宿主 logger，**留存取决于宿主日志是否可检索**，这一条要在读数时才作数。
2. **空池率**：池为空 / 首位得分极低的比例。它抓的是灾难性失效——池常年为空 ⇒ 候选永远不出现 ⇒ 整个特性静默失效。
3. **池组成（hubness）**：同一篇文档在若干次候选里反复占据首位的比例。第二轮实测里词法排序被单篇文档统治到 105/125，正是「K 越大反而越差」的原因；改用读层排序后这个数仍要盯着——它是比「同标题模板」大得多的噪声源。
4. **一致性率**：把「本会话被检索/注入过的条目标识」与「候选池里的标识」对照记录。**无需标注**，且问的正是写层要回答的问题：模型刚看过的那个，有没有出现在候选里？
5. **下判是否看过全文**：模型在下判之前有没有拉过该候选的全文（从工具调用序列就能判），以及判词分布。这是唯一能回答「短标签会不会让模型变懒」的观察物（见 D12b）；与第 4 条一样，它只记录，不改变行为。
   **实现时收窄了一处判据**：「看过」问的是**模型没有刚写下的那一端**。对路径（`mem_compare`）的第一个参数就是本次保存落库的那一条——它刚被写出来，正文就在模型手里，要求它再拉一次全文会让每一次下判都显得是「盲判」。所以实现记下本会话保存过的标识，`readFirst` = 该对里**除这些以外**的标识都拉过全文；只带关系标识的调用（两步撤销那一步）计入判词分布、不猜「看过没有」。

**刻意不做**：候选召回率的研究。卡点不在算力而在**标注**——现有 147 条 judged 真关系正是上游机制**已经找到**的对（按构造词法相近），我们真正漏掉的对因为没人判过所以不在集合里 ⇒ 这个样本会美化任何池，对词法池美化得最厉害。它唯一站得住的用法是**同一批样本上比较两个池**（偏置对两边相同），要留作将来换池时的对照可以，但不得被当成「召回率」引用。

### D10 范围裁定

| 项 | 裁定 | 理由 |
|---|---|---|
| 读层认判决 | **单独变更** | 它动的是读层最稳的契约；且关系是**廉价旁读**（查询期另开只读连接读关系即可，判决落库后下一次查询就可见），不需要重建索引、不需要改 `source_hash`、不需要把关系折进索引 |
| `pending` 机制 | 不搬回来 | 使用者裁定；且消费端一律要能忽略它（真库现有 13 行） |
| 写入面本机暴露 | 出范围 | 使用者判为额外增强 |
| 与上游 v2 赛跑 | 出范围 | 按 1.20.0 基线做 |
| 召回率研究 | 不做 | 见 D9 |

（D7 的更正带来的收窄：撤销对**同回合写下的**关系已经可达，所以「读层要不要露出关系行标识」这个问题只剩**旧关系**的撤销需要它——留给读层那个变更，不再是本变更的前置。）

### D13 预算次序：工具静态超时按**最坏路径**派生（二审提疑、三审证实）

候选在**写入之前**算 ⇒ 两者串行，且都在这一个工具调用里。宿主的截止执行者读的是工具定义里的 `timeoutMs`（`@deepseek-ai/dsh-tool-call-timeout-policy` 读 `definition.timeoutMs`；`@deepseek-ai/dsh-tools` 只是声明它）。

**我第一版把公式写成「候选预算 + 写入超时 + 余量」，这是一个真洞**（三审证实）：回退路径要发起一次**内部 MCP 保存调用**，而桥的 MCP 客户端**每次请求的超时是连接上的固定值**（来自共享的 `toolCallTimeoutMs`，默认 60 s），`callTool` 没有 per-call 超时参数。于是最坏路径的上界是「候选预算 + 写入超时 + 最多 60 s」，而静态超时只覆盖到第二项 ⇒ 走回退时宿主的截止会在内部调用结算之前到点。更难救的是第二层：宿主策略在自己的计时器先到时会把**已经结算的结果替换成超时错误**，所以「让回退忽略截止跑完」也救不回来。

三条改法（都已落进 spec / tasks）：

1. **静态超时按最坏路径派生**：`T = 候选预算 + 写入超时 + 回退调用预算 + 余量`，并断言 `T` 覆盖最坏路径（正向断言，可测）。
2. **回退调用拿一个显式、独立的小预算**，不继承共享的 `toolCallTimeoutMs`（否则 `T` 被塞进 60 s，保存的截止变长且与其它工具耦合）。客户端没有 per-call 超时，实现要自己合成 deadline；超预算即放弃。
3. **spec 里那句绝对句要收口**：「回退不让保存失败」限定为「回退路径可用且在它自己的预算内」；两条路都不可用时如实失败——这与已生效的「engram 不可用时降级」并不冲突，先前那句是没有兜底的绝对句。

另有一件同源的事：宿主的取消是**协作式**的，所以桥 SHALL 把调用给的取消信号一路传进写入请求与候选查询（后者的入口现在还不接信号，实现时要顺手接上）。

### D11 工具面数字

engram 声明 22 个工具；刻意不注册的从 3 个变为 4 个（新增「被桥自有保存入口取代的写入工具」）⇒ 桥自 engram 声明的工具 18 个；插件自有工具从 2 个变为 3 个（检索、追索引、保存）⇒ 模型可见的 `mcp__engram__*` 合计 **21 个，与变更前相同**。

### D12 证据的形状：机械谓词填空，不需要生成式模型

使用者的问法是「桥插件里又没有大模型，怎么给人话」。答案是：**「人话」不是生成句子，而是固定枚举的句子 + 机械谓词填空**。插件手里本来就有全部事实，它只负责把它们摆成一行行可读的短语；**判断由模型在自己的回合里做**——这正是「机械挑候选、交还 Agent 裁决」的落实。生成式措辞是被刻意排除的：一旦插件写出「这条看起来是它的新版」，那就是机制在裁决语义（笔记的硬边界）。

证据的枚举（每条都由一个机械谓词决定，不需要任何模型）：

| 证据行 | 从哪里来 | 谓词 |
|---|---|---|
| 共享的稀有词：`派生索引 / 覆盖加成 / hubness`（最多列几个，按 IDF 从大到小） | 派生索引的 postings / terms（已在算排序时拿到） | 两边 token 集合的交集，取 IDF 最高者 |
| 共享 N 个稀有词（N=0 时明说） | 同上 | 交集大小；**N=0 是关键信号**：只有语义那一半能捞到它 |
| 同一个主题键：`xxx` | **正本**（索引里没有这一列） | 两侧 `topic_key` 非空且相等 |
| 同一次会话 | **正本** | 两侧 `session_id` 相等 |
| 同类型且标题完全相同（疑似模板） | 派生索引 | `type` 与 `title` 都相等 |
| 语义名次第 r（共 N 条） | 排序本身 | 机械名次，而不是相似度原始值 |
| 本次将更新它（升版 / 去重命中） | 写入响应的标识 | 与既有记忆的标识相等（见 D3 的分支） |

「更早 / 更晚」这一行**被删掉**（复核指出它退化）：候选是写入**之前**算的，新行那时还不存在，所以「候选更早」恒真、「更晚」不可达，它不携带信息；方向由 D7 的参数约定承担，不靠时间比较。

**这次有界回读发生在常驻进程里**（复核指出材料没写）——它已经会读正本（索引就是那么建的），把「取 `topic_key` / `session_id` / `normalized_hash`」和候选排序放在同一处，宿主只负责渲染；这样宿主入口的 import 闭包不会被牵进 SQL 层（硬规则 7 的边界机制仍然只看 import 闭包）。
| 内容完全相同 | 派生索引的 `content_sha` | 哈希相等 |

两条**新数据依赖**，都是为了这张表（其余各行用索引就够了）：

1. **按候选 id 有界回读正本一次**：只为拿 `topic_key` / `session_id`。最多读候选池那么多条（K），一条 `IN (...)` 查询，只读句柄。
   被否的备选：把这两列折进派生索引——它们变化频繁（`topic_key` 每次升版都要改派生数据、`session_id` 每条都要写），等于把「廉价旁读」塞进「贵索引」，还要多一次 schema 升版与全量重建。
   **一处与任务书的偏差，记在这里**：任务 3.3 把回读的列写成 `topic_key` / `session_id` / `normalized_hash`，但规范结构里没有 `normalized_hash` 的落点（「内容完全相同」按 D12 取索引的 `content_sha`，它是 `title\0content` 的哈希）。取一列不用是死代码，所以实现只取前两列；`normalized_hash` 是**去重键**的一部分，而那个判断已经由「写入返回的标识 + 写前候选集」承担（D3），不需要第二次近似。
   **`same_topic_key` 的类型**：它不是布尔而是「共享的那个键本身」（不共享时是**空串**）——投影要写出键名，而「数值必须能追到具体物」对每一行证据都成立。**不能用 `null`**：宿主的 JSON schema 执行子集只允许**一个标量 `type`**（`type: ['string','null']` 会以 `JsonSchemaError` 让**整棵插件树加载失败**），这条是**真机加载时才暴露的**，见文末「实现缺陷」一节。
2. **共享稀有词**这一个信号要跟着排序一起算出来（它本来就在算词法分时路过），不需要额外读。

呈现上**不出现插件内部的排序分数**（`0.7312` 这种）。理由不是洁癖：词法那部分随新文本长短变化，**跨次不可比**，摆出来会让模型把「第 40 名」读成「挺像」。要给强弱，就给**名次**——名次是机械的、可比的、不需要校准。

**规范值就是结构，模型看到的是它的投影。** 候选的规范化值是每条一个结构（进会话日志与工具结果的结构化部分），渲染函数把它投影成紧凑标签行；测试同时钉住结构字段与投影措辞。这与读层「规范值 + 渲染函数」的形状一致。

```js
{ id, title, type, updated_at, will_update,
  same_topic_key, same_session, same_type_and_title, identical_content,
  shared_rare_terms: { count, terms: [...] },
  semantic_rank, corpus_size }
```

命名守则（防的是「把判断塞进字段名」）：**中性谓词**——用 `same_type_and_title`，**不用** `template_like`；「疑似模板」这类词也从渲染里删掉。与之配套的一条：**数值必须能追到具体物**——只给 `shared_rare_terms.count` 会被误读（那 3 个词是主题词还是口头禅？），所以要把**那几个词本身**列出来。

### D12b 候选出现时的动作提醒：附在工具结果里，不另做注入

问题：候选出现时，能不能临时提醒模型「下判要慎重」。**能，而且最合适的位置就是这次保存的工具结果本身**——那是我们自己的工具，渲染由我们掌握。

| 通道 | 为什么不用 |
|---|---|
| 常驻提示词段 | 它按契约为**逐回合恒定**（见 `engram-protocol` 的「常驻文本的内容与次序稳定」），不能按某次保存的返回值变化 |
| 技能正文 | 按需加载。**没加载技能的会话照样会保存**，于是候选出现时模型手里一条判法都没有——这正是需要提醒的原因 |
| 往收件队列塞一条消息（压缩召回那条路） | 它要等下一个 step / 回合才被领取，而「判」要在这一个 step 里做；投递本身还可能被取消或 disposal 丢掉，唤醒还会惊动 driver——为一个提醒付这些不划算 |

因此：**有候选时，结果末尾附一句固定的、讲动作的提醒**（不讲结论、也不重述判法——判法仍只有技能正文 §4 一处真相，提醒只指向它）。措辞与「有候选才出现」由渲染函数保证并被测试钉住。

**第一版措辞被使用者否掉了，值得记下来**：我写的是「把握不足时先问使用者」。它**默认了"可以留着以后问"**，而在本变更的形状里候选不重发（D6），跨回合就等于错过窗口。改法是让"问"变成**同回合且自足**的动作：

```
以上候选需要你裁决：下判前先读候选全文；没把握就别记录。
要问使用者，就在本次回复里问、并带上候选编号——候选不会重发。
```

三处判据借此写清：

1. **"问"必须在本次回复里发生**，并把**两个标识都写进问题**（本次保存的那条与候选那条）——二审指出只带候选编号时，方向锚（本次落库的标识）可能被压缩带走，下一回合就构造不出方向正确的关系；两个都写进问题，答复回来时这一对是完整的。
2. **问的是"会改变以后检索结果"的那类判断**（取代 / 冲突）——具体判据仍在 §4，提醒不复制它。
3. **错过窗口的代价是"这一次不记"，不是"永久失去"**：池是每次保存重算的，下次保存近似内容时同一条候选会再出现。这是"候选不落库"最要紧的安全性质——**没有 pending 行，也就没有必须偿还的债**。

**它防不了的一件事，因此要靠仪表**：一句话并不能阻止模型看一眼摘要就下判。真正的观察物是「模型在下判之前有没有拉过该候选的全文」——从工具调用序列就能看出来。这条进 D9 的仪表。若日志显示「从不拉全文、却每次都在判」，那就是真懒，届时再改（把提醒变成硬性顺序，或把证据降到只够触发一次拉取）。

### D14 会话标识与项目：保存入口走**既有那一套**注入，不为它特判

我先后提过两种特判，都被否掉了，记在这里以免再走一遍：先是「保存用后端解析的项目、覆盖不作用于保存」（使用者：那是发明第二套规则）；后是「保存不声明这两个参数、由桥自带绑定值，好让开关关掉时保存仍成功」（使用者：与 recall 对齐、少写新代码、少发明新规则）。

**最终裁定：保存入口声明 `session_id` 与 `project`，与 recall 及 engram 工具走同一套注入**（`src/injection.ts` 的通用实现按"该工具自己声明的参数"决定注入什么，零新增取值代码）。注入被关闭、调用方又没显式传值时，**以明确原因拒绝**——形状照抄 recall 在同情形下的拒绝（说明缺哪个值、有哪两条出路），不落库、不静默改用别的值。

**这一条要如实记账的行为变化**：`injectSessionId=false` 今天就已经让写入失败（上游 `mem_save` 拿不到会话，被后端拒），所以这里只是把同一个失败换成更清楚的说明，**不是回归**；但 `injectSessionProject=false` 今天在上游 MCP 路径上**仍然能写成功**（后端自己从会话推出项目），而按本裁定保存会被拒——这是**一处刻意的行为回归**，换来的是"一条规则"而不是"两条"。它要写进 README 与升级清单，让使用者知道这两个开关现在会挡掉保存，以及两条出路（显式传值 / 打开开关）。

## Risks / Trade-offs

- **默认环境可能没有 HTTP 写入面**（复核抓出）：插件默认 `args: ['mcp']` 只起 stdio，写入面要求 `engram serve` 在跑；不跑 serve 的机器上本特性 100% 走回退，于是「不新增待判行」在那台机器上不成立（验收信号已限定为「写入面可用时」）。这条是**前提而非缺陷**，但必须写进 README 与升级清单。
- **回退路径要满足与新路径同样的结果义务**（二审抓出）：上游保存工具的返回是**纯文本信封、没有结构化字段**，所以「本次落库标识」和 `will_update` 只能**解析信封**得到（标识在信封里），而它自己那套候选要被丢弃。回退不是边角（见上一条），这条必须有验证。
- **来源标记不是回退的充分证据**（二审修正）：响应超时那条路可能已提交，行上带着标记却仍走了回退；判据是结果文本 + 日志（见 D8）。
- **超时回退「只落一条」还带一个时间窗**（二审提示）：去重要求 `normalized_hash` + `project` + `scope` + `type` + `title` 全部一致**且在该后端的时间窗内**（默认 15 分钟）。超过窗口的补写会落成第二行——这条进升级清单的复测项。
- **回退路径与候选的关系**（复核抓出）：回退走上游保存，而那条路径自己会返回它那一套候选与判定标识。裁定：**结果里不转述它们**（本插件自己的候选照常给），日志里记下回退；否则本次要根除的东西会从回退这条路漏回模型眼前。
- **两条路径的归一化必须由桥统一**（复核抓出）：缺省 `type` 与 `observation` 别名若只在一条路径上补，超时回退会落成两行（去重条件含 `type`）。这是「只落一条」那条契约的前提。
- **冷进程的第一次保存没有候选**（模型加载被短预算截断）。接受：宁可少一次候选，不可让保存卡住。
- **池的全库召回没有读数**（已知未知）：它继承「检索当时能找到什么」，而这正好是写层的任务边界——把模型本来会认出来的东西摆到它面前。
- **回退时仍会产生 `pending` 行**（服务不可达时走上游路径）。因此消费端必须忽略 `pending`，这一点与「我们不再制造它」不冲突：真库里本来就有 13 行来自其它路径。
- **误记「取代」无工具面撤销入口**（见 D7）。缓解是协议的「先问使用者」。
- **协议文本的改动需要重新加载插件才对在跑的宿主生效**，与读层先例相同。

## Open Questions

- **M 的默认值**：第三轮给出建议 **M=5**（约束 B ≥ M，B 复用检索自己的默认值），但它只把展示精度在 14.4%–17.6% 之间挪动，最终值要在实现后用 D9 的仪表择定。
- 冷进程的第一次保存没有候选，这个体验是否需要额外处理（例如让第一次保存顺带把索引追到最新）——本次按「不追」实现，等读数。
- **旧关系**（不是同回合写下的那些）的撤销是否需要工具面入口——需要读层露出关系行标识，留给读层那个变更。
- 上游保存路径的 `not_conflict` 是**空结果**而非错误，且它是最常见的判决；语义已写进 spec、并由任务按**零增量 + 不返回新的关系标识**验证。**要不要再让桥在结果里补一句人话说明**（那需要在「结果透传」契约上开一个例外）留作将来可选，**不再阻塞本变更**（二审指出原写法把一条做不到的 SHALL 留在了 spec 里）。
- **已知未知**：本机是否真的挂载了宿主的工具调用超时策略（`dsh-tool-call-timeout-policy`）——D13 的派生前提依赖它；验收时顺带确认一次，未挂载则该前提不成立（超时不会被强制执行）。

### A. 两条写入路径逐项对照（任务 2.3）

同一批入参分别经 HTTP 写入面与 MCP 保存入口落进同一张隔离库，逐项比对：

| 项 | HTTP `POST /observations` | MCP `mem_save` |
|---|---|---|
| `observations` 增量 | +1 | +1 |
| **`memory_relations` 增量** | **0（无 pending）** | **+1 pending** |
| FTS 触发器（`observations_fts` 命中数） | +1 | +1 |
| `sync_mutations` 增量 | +1（仅观察） | +2（观察 + 关系） |
| `session_id` / `project` / `scope` | 与请求一致（`probe-session` / 项目名 / `project`） | 同 |
| `type` / `title` / `content` / `topic_key` | 与请求一致 | 同 |
| `revision_count` / `duplicate_count` | 1 / 1 | 1 / 1 |
| `review_after`（type=`decision`） | 有值（+6 个月） | 有值（同一偏移） |
| `normalized_hash` 长度 | 64 | 64 |
| `tool_name` | `dsh-engram-bridge` | `NULL` |

- **`topic_key` 升版**：两条路径各自「同键写两次」都返回**同一个 id**、`revision_count` 都变成 2。

## 实现缺陷：一条把整棵插件树带下去的 schema（2026-09-19，真机加载暴露）

**症状**：任何装了本插件的 profile 都开不了机——

```
dsh: plugin tree failed to load: failed to apply loader entry engram-bridge (dsh-plugin-gentleai-engram):
unsupported JSON schema: schema.properties.candidates.items.properties.same_topic_key.type
must be a single type string (type arrays are not supported)
  at assertSupportedJsonSchema (dsh-tools/lib/index.js:325)
  at Proxy.register (dsh-tools/lib/index.js:2777)
```

**根因**：`same_topic_key` 写成了 `{ type: ['string', 'null'] }`。宿主执行的是**JSON schema 的一个子集**（`dsh-tools/json-schema`：一个标量 `type`、对象 `properties`/`required`/布尔 `additionalProperties`、数组 `items`、标量 `enum`/`const`、恰好一个 `oneOf`），类型数组**直接拒绝**，而且拒绝发生在 `ctx.tools.register` 里 ⇒ 插件 apply 抛错 ⇒ 整棵树加载失败。修法：`same_topic_key` 用**空串**表示「不共享主题键」，`type: 'string'`。

**为什么仓库里的门禁没拦住（四条，逐条记下来免得再犯）**：

1. **假宿主不校验 schema**。三个 wiring rig 的 fake host 只把定义塞进 Map，从不调用宿主的 `assertSupportedJsonSchema`。
2. **`--dump-config` 不加载模块**：它只打印组合树，正是 README 说的「不 boot」。
3. **冷缓存时连注册都不会发生**：`registerTools` 有两条触发路径——缓存水合（`apply` 时同步）与发现（异步，先连上才注册）。冷缓存的 boot 在凭据检查处就退出了，我们的工具定义**根本没交到宿主手里**，于是「能启动」是假绿。真机（用户的 profile）是**热缓存**，一次 `ctx.tools.register` 就把整棵树带下去。
4. **headless 的凭据检查早于任何模型请求**：作者最初的「在 headless 里试一下」之所以什么都没试出来，就是因为它只跑到缺 API key 那一步。

**改法与守卫**：

- 新增 `test/tool-schema-subset.test.ts`：用**宿主自己的** `assertSupportedJsonSchema` / `assertObjectJsonSchema` / `validateJsonSchemaValue` 跑遍我们交给宿主的每一个 schema（六个常量 + 三条注册路径实际产出的定义 + 工具面 fixture 的声明），并且**用真实值**校验一次保存结果（含 `''` 哨兵、`fallback`、缺 `id` 三种形状），再加两条反向对照（类型数组、`type` 与 `oneOf` 同时出现）——守卫自己也得会红。
- **真机复现与验证**（工作区里的 throwaway `DSH_HOME` + 从 `headless`/`web` 模板起的 probe profile，符号链接指回本仓库；没碰使用者的 profile 与数据）：
  - 把类型数组改回 `dist/`、**热缓存**下启动 ⇒ **逐字复现**上面那段错误，栈同样落在 `Proxy.register`；
  - 改回单类型 ⇒ 同一个 harness 下 headless 走到「缺 API key」（即插件树已加载），web 档能起来并打印自己的 URL。
  - 冷缓存下两者都「通过」——这正是第 3 条说的假绿，所以这个 harness 的判据必须是**热缓存**。
- 记账：**这条缺陷只有真机启动才发现**。往后的判据是「改完 schema 先在热缓存的 probe profile 里 boot 一次」，而不是只看仓库测试。
