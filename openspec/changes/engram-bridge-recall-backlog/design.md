# 设计：一次检索要做多少工作 → 谁自动做 → 谁都不自动做就拒绝并指出显式入口

## Context

读层今天把派生索引的更新放在**检索调用内**完成：`RecallEngine.query()` 先读正本快照并算出差异，再由 `IndexDb.sync()` 嵌入变化过的文档，最后在同一个 SQLite 事务里提交。这条路上已经写下三条要求（`openspec/specs/engram-bridge-recall/spec.md`）：

1. 变动后紧接着的下一次检索必须可见；
2. 更新必须原子（要么整体生效、要么整体不生效）；
3. 每次调用有预算（`searchTimeoutMs`，默认见 `src/config.ts` 的 schema；工具侧比它多 10 s，见 `src/index.ts`）。

**嵌入就是全部成本。** 稳态检索约 11 ms（数百条语料）；一次全量重建里，读正本约 6 ms、纯索引构建（分词 + 倒排 + SQLite）约 190 ms，其余全是嵌入。所以「要做多少工作」几乎就等于「要嵌入多少条」。

三条要求在大 delta 下互斥：一次调用做不完的积压，只能违反其中一条。今天的实现违反了第 3 条（超时被杀）或第 1 条（部分不可见），并且把违反表达成一个失败区间：

- `sync()` 在 `touched > MAX_INLINE_SYNC_DOCS = 500` 时抛 `BacklogError`（干净拒绝）；
- 但 1 线程的行内嵌入在预算内只能做约一百多条（平台不同），于是中间这一档既超时又不够报错：**嵌入在事务之前发生，进程被杀即零进展**，下一次调用从零重来 → 活锁；
- 而 `ensureIndex()` 判定派生数据不可信时，会把整件事交给一个**完全没有上限**的一次性子进程，唯一的边界是同一个 `searchTimeoutMs`——语料超出它的预算时同样是超时被杀 → 零进展。**两条悬崖其实是同一个**：工作量 > 最快可用进程在预算内能做的量。

触发条件是**滞后时间**，不是语料规模。离线一段时间的机器、或别的 agent 在写而本机没检索，lag 一样攒。

命名诊断：`MAX_INLINE_SYNC_DOCS` 用**执行轴的名字**执行**数据轴的判定**（`mode === 'incremental'`）。今天两者巧合重合——所有重建都由 recall 触发，不存在「显式全量重建」这个操作，所以「inline vs 全量」不是一对替代项。真实只有一根轴：**要做多少工作**。

**并发上今天是空的。** 常驻 worker 内部把请求串起来（`worker.ts` 的 `chain`），但重建路径整个绕过它，且没有任何互斥/去重：两个并行（甚至只是排队）的检索会各自起一个全量重建子进程；`stop()` 先 `this.child = undefined` 再等退出，窗口期里新来的请求会起一个新常驻进程，而重建子进程随即 `recreate()`（unlink 索引文件）；重建期间来的第三次检索又会因为打开半重建的索引而再起一个重建。跨进程更彻底：同一台机器上多个 profile 共享索引目录，两个宿主之间没有任何锁，`IndexDb.open()` 也没设 `busy_timeout`（撞写锁直接 `SQLITE_BUSY`）。

## Goals / Non-Goals

**Goals**

- 一条规则覆盖全部情况：算工作量 → 自动路径 → 拒绝并指出显式入口。
- 「需要重建」不是特例，而是「工作量 = 整个语料」的同一条判定。
- 常规检索**不再静默承担大延迟**：等待变成调用方的显式选择。
- 同一份派生数据同时只有一个写入者，跨进程，且持有者被杀后可安全接管。
- 常驻内存不变；不新增配置键；不按平台分支；要求 1、2 不动。

**Non-Goals**

- 不做后台/主动同步，不做写侧钩子，不监视 engram（engram 不提供推送侧）。
- 不改 engram、不改派生索引格式或打分、不改嵌入模型与运行时。
- 不解决"另一个 profile 的常驻进程握着旧 inode 作答"这类**只读侧**的跨进程陈旧（见「已知未知」）。
- 不引入按身份分目录（多 profile 共享派生状态那条线）。

## D1 一条规则：工作量 → 自动 → 拒绝

判定只需要两个量：**Δ = 本次要嵌入/删除的条数**（索引不可信时 Δ = 整个语料），以及**自动限额**。

```
Δ = 正本与派生数据的差异（索引不可信时 Δ = 全量）
  ├ Δ = 0                 → 直接作答
  ├ Δ ≤ residentCapacity  → 常驻进程自动做完（增量与全量同一条路）
  ├ Δ > residentCapacity  → 拒绝：附「显式入口 + 待处理条数 + 预估秒数」
  └ 显式入口被调用         → 做完（它自己也有单次上限，超了当场拒绝）
```

**为什么是「两条路径」而不是「按 Δ 决定线程数」**：线程数在进程内改不了——`ort.env` 是模块级单例，WASM 线程数在运行时初始化时定死。同一进程里先建 1 线程再建 16 线程，第二个不生效。所以「按 Δ 决定线程数」只能意味着「决定由哪个进程服务」。

## D2 `sync` 只做机制：上限是参数，`deferred` 是结果

`SyncOptions` 增加 `maxDocs?: number`（缺省 = 无限，即机制默认不设限），`SyncMetering` 增加 `pendingDocs`，`SyncMode` 增加 `'deferred'`：

- 差异先算（位置本来就对：diff 早于嵌入，已是预检退出、零提交）；
- `touched > maxDocs` → **返回** `mode: 'deferred'` + `pendingDocs`，**什么都不写、不抛错**；
- 否则照常嵌入 + 单事务提交。

**上限对 `full` 同样生效。** 这正是两条悬崖合一的地方：今天 `full` 的唯一边界是子进程超时，而超时 = 被杀 = 零进展。把上限放进 `sync` 的机制里、不区分 `mode`，`full` 就自动获得「放不下就拒绝」的能力。`mode === 'incremental'` 这个判定条件随之删除，`MAX_INLINE_SYNC_DOCS` 与 `BacklogError` 一并消失。

**机制的隐式缺省（不写 `maxDocs` 时不设限）只给测试夹具用，没有任何产品路径可以走它。** 上限有两条载体，都钉死：

- **常驻**：实例生命周期内是常量，所以走 spawn 时的环境变量——`childEnv(threads, maxDocs)` 给常驻也写 `ENGRAM_BRIDGE_MAX_DOCS = embedCapacity(searchTimeoutMs, embedThreads)`。`workerConfigFromEnv()` 对这个键**不设 fallback**：缺失就按硬规则 4 响亮失败（否则"缺省 = 不设限"会从后门回到产品路径上）。
- **一次性**：同一个键，值为 `embedCapacity(ONESHOT_TIMEOUT_MS - ONESHOT_MARGIN_MS, rebuildThreads)`。
- **操作者命令**（D8）：同一个键，值是显式的字面量 `unlimited` ⇒ 省略 `policy.maxDocs`（不是缺省、不是数字）。`workerConfigFromEnv()` 显式认这个字面量——别用 `0`/`-1` 这类会被数值解析吞掉的哨兵。它是一条**有意**不设限的产品路径。
- `RecallEngine.query(request, policy?)` 的 `policy` 保持**可选**（缺省不设限）——那是给测试夹具的；worker 的两个入口（查询与残留的 `cmd: 'rebuild'` handler）**总是**传 `this.config.maxDocs`。这样 spec 那句「『需要重建』SHALL NOT 单独走一条不受限额约束的路径」在契约层成立，而 24 处既有 `engine.query({...})` 调用点不必逐个改。

改这个键（以及锁等待窗口）要动**全部六处 spawner**：`process.ts` 的常驻与一次性两处、`scripts/mem-profile.mjs` 的两处、以及 `test/recall-worker-reload.test.ts` 的两处（`startWorker` 与 `rebuildExit`）。

## D3 没有自动转交：大的工作只能被显式请求

第一版设计里 Δ 落在「常驻限额以上、一次性进程预算以内」时是**自动转交**的。砍掉它的理由是它自己的原则：那一档会让一次 recall 静默地卡 8–51 s（外加两次模型加载与进程启停）。限额存在的理由不是"做不了"，而是"常规回合里不想插入大量延迟"——那么**未经同意就插入**是最糟的组合。等待应当由唯一能判断的 actor（调用方）显式选择。

代价照实记：

- 原本"离线一个月"的主案例现在需要两次调用（显式入口 + 重发检索）。它**依赖调用方行动**：如果调用方把拒绝吞掉直接作答，系统就是静默退化的。所以拒绝文本与工具描述从"说明"升级成**载荷**——工具名、待处理条数、预估秒数、"派生数据没有被改动"、"完成后请重发本次检索"。`searchTimeoutMs` 在文案里只能作为**自动限额的旋钮**提一句（调大它会让更多工作落进自动路径），它不是"把大工作做完"的旋钮；主要出路永远是显式入口。
- 收益是结构变小：`query()` 里不再有 `stop → spawn → 重启 → 重试一次`，也没有"重试又 defer 怎么办"这条边界。`query()` 只剩：算、做、或拒绝。

## D4 限额怎么算：一个保守的「每线程每条」常数

实测（每台机器一次；方法与陷阱见本节末）：

| 平台 | 1 线程 | 16 线程 | 16/1 |
|---|---|---|---|
| x86-64 桌面机 | 334 ms/条（2.99 条/s） | 39 ms/条（25.7 条/s） | 8.6× |
| arm64 笔记本 | 约 556 ms/条（约 1.8 条/s） | 约 64 ms/条（约 15.7 条/s） | 约 8.7× |

并行加速是**次线性**的（16 线程只换来 8.6×），所以"每线程效率"随线程数**下降**：单线程时最优，16 线程时最差。一个在所有测量点上都**不乐观**的每线程常数必须取最差的那个点：

```
K = ceil( max over 测量点 ( ms/条 × 该点线程数 ) × 安全系数 / 100 ) × 100
  = ceil( max(556×1, 64×16 = 1019, 334×1, 39×16 = 624) × 1.27 / 100 ) × 100
  = 1300 ms·线程/条                      ← 常数本身取整到 100，避免容量随小数漂移

容量(路径) = floor( 单次预算 ÷ K × min(该路径线程数, 16) )
```

**线程项必须夹到测量范围**（`min(threads, 16)`）。四个测量点最高只到 16 线程，而并行是次线性的，`threads > 16` 的线性外推方向正是**乐观**——`embedThreads` 这个键在 schema 里没有上界（`min(1)`，无 max），不夹住就等于给"用户把它调到 64"留了一条回到活锁的路。

安全系数覆盖模型加载、索引构建、快照与抖动。由此：

| 路径 | 线程数 | 预算 | 上限 |
|---|---|---|---|
| 自动（常驻） | `embedThreads`（默认 1） | `searchTimeoutMs`（默认 60 s） | **46 条** |
| 显式入口 | `rebuildThreads`（默认 `min(16, availableParallelism())`） | 该工具声明的超时（拟 10 min）**减去 15 s 余量** = 585 s | **7200 条** |

「减去 15 s 余量」是一个具名常量（`ONESHOT_MARGIN_MS`），被容量推导与工具声明两处共用——否则"10 min"与"585 s"会各自漂移。

边界上的自证：常驻上限 46 条在 arm64 上实测级约 26 s、保守估计正好落在预算内；显式入口上限约 7200 条远大于任何真实积压（按活跃写入速率，约等于一年半不检索）。

**为什么不按平台分支**：一个常数在四个测量点上都不乐观，就不需要知道自己在哪台机器上——这正是 `MAX_INLINE_SYNC_DOCS` 的教训（那根轴今天巧合重合，加第二个调用者即失效）。

**"738"不见了**：它只属于被砍掉的自动转交那一档；现在一次性进程只有显式入口一条路，它的上限由 `ONESHOT_TIMEOUT_MS`（D7）决定，没有独立的"预算"概念。

**读数的方法与陷阱**（复测时别再踩）：

- 别拿首次查询当基准：`ensureIndex()` 的完整性检查是一次性成本，计入 `totalMs` 但不单独计量。必须同一引擎连查多次、取第 2 次之后。
- 别把 16 线程路径的速率套到 1 线程路径上——两者相差 8.6×，混用会把限额算大 8.6 倍。
- 读数只留速率（机器指纹，可复用），不留语料规模与时刻。

**K 的前提不是"平均文档长度"，而是"单条成本有硬上界"。** 截断发生在 post_processor 之后、`model_max_length`（默认 512）处，所以单条嵌入成本封顶；读数语料里已经有过半文档触顶。也就是说长度**推不动**成本：按"过半触顶、其余减半"粗算，最坏（全部触顶）相对标定均值的偏斜约 **1.18×**。默认路径的余量是 2.34×（K=1300 vs arm64 实测 556 ms/条，46 条只用 25.6 s / 60 s），安全；**显式入口那一档的余量只有 1.27×（就是安全系数本身，它还要覆盖身份判定、进程启停、索引构建与抖动）**，1.18× 会吃掉大半。所以退回条件写成"复测时记录**触顶比例**；若几乎全触顶则抬高 K，或把 16 线程那条读数改在全触顶语料上取"，而不是"平均长度变长"（那条在 512 截断下不可达）。

## D5 限额内的全量重建由常驻自己做

今天 `ensureIndex()` 一判定索引不可信就抛 `rebuild-needed`，整段交给子进程。若沿用，就会留下一条**绕过限额判定的暗道**：语料 3 条、索引被删也要走显式入口，而语料 3000 条、只多了 5 条变化却由常驻消化。同一件事（不可信 vs 内容变了）被两种待遇，正是这次要消掉的那种特例。

所以：**不可信索引下重新建立派生数据，就是 Δ = 整个语料的那一次**——Δ 在限额内时由常驻就地全量同步，超出时才拒绝并指出显式入口。这要求常驻获得"重建"的能力（今天它连不可信的索引都不开）。

**顺序必须钉死（与 D6 的锁一致）：拿锁 → 立刻 `close()` + 置空（丢掉 `ensureIndex()` 缓存的句柄）→ 锁内 `readSourceState` + 重新 inspect → 算 Δ（不可信时 Δ = 全量）→ 比限额 → 只有不超限才做全量同步。** 两个坑都要躲开：`close()` 若被推到限额判定之后，缓存句柄还在、`inspectIndex` 根本不会跑，锁内读到的就是旧 `source_hash`（D6 警告的那个"Δ 算成 0"）；而销毁若被提前到限额判定之前，拒绝时索引已经被清空——`source_hash` 变 `''`，此后每次都算 Δ = 全量，用户再也回不到增量，而「拒绝不改变状态」这条契约当场被违反。

**"销毁重建"用 `sync({ full: true })` 就地做，不用 `IndexDb.recreate`。** `recreate` 是"unlink 三个文件 → 新建 → **单独提交**一个空索引（`source_hash=''`）"，与随后的全量同步不在同一个事务里：两者之间被 SIGKILL 就留下一个"空而有效"的索引，那不是"并发失败"，而是**状态被改掉且没人能自动恢复**（大语料下接管者是一条常规检索，它会再次按限额拒绝）——「在更新成功之前，检索 SHALL 与上一次成功更新后的状态一致」当场不成立。而 `sync({ full: true })` 已经在**一个事务**里清空 + 重写全部行 + 重写 meta，就地做即可。顺带消掉两件事：`-wal`/`-shm` 被并发 unlink 的隐患，以及 DB inode 的漂移。代价只有一条：文件不收缩（不做 VACUUM）。`recreate` 只留给"文件缺失/不可读/`integrity_check` 失败"——那时旧状态本来就不可读，没有"上一次成功状态"要保。于是：

- 小语料下"删掉派生数据即自恢复"这条既有承诺照旧成立；
- 大语料下它变成一次显式调用，而不是多出一条规则。

## D6 锁：同一份派生数据同时只有一个写入者

**落点在写入者进程里**（常驻的内联同步、显式入口的一次性子进程），包住 `读正本 → diff → 嵌入 → 提交`**整段**——嵌入也要在锁内，因为"两个重建并发"浪费的正是峰值内存（本次变更唯一没量过的数）。宿主只决定"由谁写"，不自己拿锁；它从写入者返回的错误里得知"别人正在写"。

```
锁文件：<indexPath>.lock（即 index.db.lock，与索引同目录）
内容：一行 JSON { pid, host, lastProgressAt, staleAfterMs, token }
常量：STALE_WINDOW_MS（陈旧窗口，拟 5 min）、STALE_MARGIN_MS（余量，拟 30 s）、
      LOCK_WAIT_AUTO_MS（2 s）、LOCK_WAIT_BUDGET_FRACTION（一次性按自身预算的大半）、
      LOCK_WAIT_OPERATOR_MS（5 s）

获取：
  1. 用 'wx' 建、写入**完整记录**、**保留 fd 到释放**（心跳要用它；释放时一并关闭）。
     拿到锁的判据是"**按路径**重读，内容仍是自己的 token"——读回只用于判定，不用于心跳。
  2. EEXIST → 读内容判陈旧（**三条钟表判据都只适用于同机；跨机不在支持范围内**，见「已知未知」）：
     - 同机且 pid 不存活                                    → 陈旧（快速路径，不必等窗口）
     - host 一致 且 now - lastProgressAt > WINDOW + MARGIN  → 陈旧
     - host 一致 且 now < lastProgressAt - ε                → 陈旧（时钟回拨）
     - 读不出/解析不了                                      → 只有比一个很短的下限（~2 s）更老才算陈旧
       （正常心跳不会被读成这种——心跳写位置 0 且写后自检，见下）
  3. 陈旧 → 只能"改名偷"，不能 unlink：
     rename(lock, lock.stale.<自己的 token>) → unlink 偷来的 → 回到第 1 步。
  4. 不陈旧 → 按调用方自己的**等待窗口**轮询（200 ms）→ 等不到就拒绝。
心跳：持有者在**每处理完一个嵌入批次之后、以及进入写事务之前**，就地重写**整条记录**：
  - 走创建时的 fd：`ftruncate(fd, 0)` → `write(fd, json, 0)` → `ftruncate(fd, byteLength(json))`。
    **必须显式写位置 0**：`ftruncate` **不重置文件偏移**，否则文件会变成 `"\0…" + JSON` 而**永久不可解析**。
  - **不按路径写**：锁已被偷走时，按路径 `writeFileSync` 会截断并覆盖**偷锁者的文件**，让双方都在写事务内复核时失败。
  - 写后立刻按路径读回、`JSON.parse`、比对 token 与 `(dev, ino)`；不符就放弃本次写入（早失败胜于被别人偷）。
写事务内复核：`BEGIN IMMEDIATE` 之后立刻比对三件事
  - **按路径 `stat`** 得到的 `(dev, ino)` 仍是自己创建的那个——**不能 `fstat(fd)`**（fd 永远匹配自己，那样偷锁检测永远不触发）
  - 锁文件内容仍是自己的 token
  - **索引 meta 里的 `source_hash`** 仍等于锁内读到的那个（不是正本快照的哈希——正本在长跑期间一直在变，比它会误报）
  任一不符 → ROLLBACK，以「正在更新」失败。
释放：只在文件内容仍是自己的 token 时 unlink，并**关闭心跳 fd**。
```

- **按路径确认**（读回只用于判定是否拿到锁）、**保留心跳 fd 到释放**、**写事务内复核**（**按路径 `stat`** 的 `(dev, ino)` + token + 索引的 `source_hash`）三者都是必需的：前者防"偷锁竞态里两个人都以为自己拿到"，中者让心跳只写进自己那个（可能已被改名/停用的）inode，后者防"锁被删掉或替换"以及"嵌入期间有人提交过"（`source_hash` 那一比还顺带挡住不认锁的旧版本进程或 `sqlite3` CLI）。**`fstat(fd)` 不能用来检测偷锁**——fd 永远匹配自己。
- 关于"让内核代管"：硬规则 7 的不变量只约束**宿主进程**（子进程允许 JS/WASM，原生 addon 是工程政策上不引入），而"内核级锁"其实有纯 JS 候选——SQLite 自己的写锁（`BEGIN IMMEDIATE` + `busy_timeout`，持有者被 SIGKILL 时由内核释放）。它没被选作唯一互斥，因为它盖不住"索引文件缺失/损坏、需要先销毁重建"那一档（那里没有可加锁的 DB），而锁文件协议一开始就覆盖全部情形；见「被否的路」。
- **`IndexDb.open()` 要按路径设 `PRAGMA busy_timeout`**：常驻 2–5 s，一次性与操作者 60 s。**不能给常驻用 60 s**——常驻一次调用的总预算就是 `searchTimeoutMs`（60 s），撞上外来写者时它会等满 60 s 才失败，而那时宿主已经把它当超时杀掉，**提交没发生 ⇒ 零进展**，正是本变更要消灭的活锁换了个地方。它与锁等待是**两条不同的等待**：正常并发在锁上就拿到「正在更新」了，`busy_timeout` 只在"刚被判陈旧的持有者正好在提交"这类罕见情形生效；两者都是 `kind: 'busy'`，**只能靠文案区分**（锁等待那条带"等待 Xms 后仍被占用，持有者最近进展 <时间>"；SQLite 那条带"索引写锁被占用，等待 <busyTimeoutMs>ms"），测试必须断言文案而不是只看 kind。另需成立 `busy_timeout + 提交耗时 < STALE_WINDOW_MS + STALE_MARGIN_MS`。
- 锁文件里的 `staleAfterMs` 是**陈旧窗口**（"多久没有进展证明"），不是"这次要跑多久"的预算：所有路径共用一个较小的常数（拟 5 min）+ 余量（拟 30 s），配合**每个嵌入批次之后、以及进入写事务之前**的心跳。于是"可以跑到完"与"陈旧可判"彻底解耦：活着且在前进的持有者不被偷（无论跑几小时），死了或卡住的在一个窗口后被接管（同机还有 pid 存活的快速路径），**不存在"永久阻塞"这条**，也不需要人工清理。
  - **不要**用"总时长 TTL"：陈旧判据与 pid 判据是"或"关系，一个大 TTL（例如 30 min）会把一次合法的长跑在半途判陈旧、锁被偷，持有者在写事务内复核时发现锁易主而回滚——整次工作作废，且第二次触发多半也已经退出，于是**两边都不完成**。那恰好违反「同一份派生数据只有一次更新在进行」。
  - **心跳窗口必须覆盖两段"最长无心跳段"**，两条都写成具名断言：`MAX_BATCH × K ÷ min(threads,16) × 安全系数 < STALE_WINDOW_MS`（`MAX_BATCH = 32`、K=1300 ⇒ 单线程最坏 41.6 s，窗口 300 s，余量约 7×）；以及 `语料条数 × ~0.6 ms（`applyDocs` + 提交）≪ STALE_WINDOW_MS`（7200 条约 4 s）。**只要有人把 `MAX_BATCH` 调到 256，单批就是 333 s > 窗口，机制会静默失效**——所以这不是注释，是断言。
  - 心跳写的是**整条记录**（至少含 `pid`/`host`/`staleAfterMs`/`token`），不是只写一个时间戳——否则"按 token 释放"与写事务内的 token 比对都会失效。写后**按路径读回自检**（`JSON.parse` + token + `(dev, ino)`），不符就立刻放弃本次写入。
  - 心跳要求写入路径**按批次嵌入**（每批之后重写记录）：这与已核验的"向量与批大小无关"相容，顺带给出进度，操作者那条请求因此能显示"已处理多少"。切片的切点属于 `sync()` 自己的 `SyncOptions.onProgress?()` 回调（由持有锁的引擎传入 `() => lock.heartbeat()`），**不要**给 `EmbedderLike.embed` 加参数——那会让测试用的 `fakeEmbedder` 静默忽略它、心跳永不触发（假阴性），而真实嵌入器还要额外实现。
- 等待策略：**自动路径只短等（拟 2 s）就拿不到即拒绝**（"索引正在被另一个进程更新"），因为它的工作本来就是秒级、等待分钟级违反 D3；**显式入口等到自己预算用掉大半**，仍拿不到才拒绝（它等的就是"别人也在做同一件事"，等完再按最新状态继续）；**操作者命令只等一个固定短窗口（拟 5 s）**，让"撞车"以明确拒绝暴露出来。三个窗口由宿主算好、**随 `childEnv` 传给写入者进程**（锁是在子进程里拿的，宿主自己不拿锁——见 D2 的 spawner 清单）。拒绝文本要带上持有者**最近一次进展的时间**（锁文件里的 `lastProgressAt`），否则调用方无法判断"该重试"还是"该调显式入口"。
- **拿到锁之后必须重新判定**（重新读正本、重新 diff、重新比限额），**并且必须让引擎丢掉它缓存的索引句柄**：`ensureIndex()` 会把成功打开的索引缓存住（`if (this.index !== undefined) return this.index`），而另一进程的 `recreate` 之后，这个句柄指向的是被 unlink 的 inode——锁内 diff 会读到旧的 `source_hash`、把 Δ 算成 0，然后拿旧索引作答。所以拿锁成功后要强制 `close()` + 置空 + 重新 inspect。计量里的 `hashMs` 也必须记锁内那次。
- `IndexDb.recreate` 只删 `index.db{,-wal,-shm}`；**锁文件必须留在原地**（持有者自己会 recreate），不要把它加进那个数组。
- 网络盘上 pid 存活判定无意义，钟表判据也只在 `host` 一致时生效 → 跨机不在支持范围内（见「已知未知」）。索引目录是本地派生状态，先按同机假设。

**它不覆盖的**：读者不拿锁。另一个进程的常驻可能一直握着被 unlink 的那份 inode 作答（WAL 语义下不算坏，但会持续从旧索引答）。这条今天就有，锁不新增也不解决，记入「已知未知」。

**重建窗口里的读者。** `recreate` 是"先 unlink 再重建"，而读者不拿锁，所以重建期间另一进程发起的检索会看到派生数据暂不可用。它按 D6 的规则**拿到锁后重新判定**，就避开了"被推去重建"；若它在自己的等待预算内拿不到锁，就以「正在更新」失败。这是本次变更在「派生数据的更新是原子的」里**显式写明**的边界：允许明确失败，不允许返回半应用的结果。（`recreate` 之后、全量同步提交之前，读者看到的是零文档 + 空 `source_hash`，只会被判为"需要重建"，不会看到新旧的混合内容。）

`tmp + 原子 rename` 能让读者在这种情况下仍读到旧索引（而不是失败），代价是 SQLite 的 `-wal`/`-shm` sidecar 在替换前后的处置需要自己验证（旧 sidecar 与新主文件的配对、`wal_checkpoint(TRUNCATE)` 的时机）。本期的取舍是：**先用"允许明确失败"这条契约把窗口说清楚**，把 tmp+rename 记为下一步的稳健性升级。

## D7 显式入口：一个工具，没有独立的预算概念

- 形状：新工具 `mcp__engram__mem_bridge_recall_sync`，无参数，语义是"把派生索引追到最新，允许长时间等待"；共享 `mcp__engram__` 前缀，子 agent 可见性自动沿用；与常规检索共用同一个引擎开关（关闭时它以同一原因被拒绝，且不加载模型、不写派生数据）。
- **一次性子进程有两种触发，同一个机制，都受限额与锁约束**：`--rebuild`（强制全量）与 `--sync`（追上：不可信就重建，否则增量）。**`--rebuild` 保留**：它的真实使用者是 `scripts/mem-profile.mjs`（内存曲线的初始化）与 `README.md` 里那条 Node 下限实测记录，`AGENTS.md` 的复测命令与 `test/package-metadata.test.ts` 的注释也提到它——删掉它等于顺手弄坏测量路径，而它想表达的只是"强制全量"，不是"不受限额"。**没有"哪种模式不受限额"这回事**：两者都拿锁、都在锁内重读、都比上限、超限都以退出码 4 退出。
- **唯一的数是 `ONESHOT_TIMEOUT_MS`（拟 10 min）**，工具定义与宿主的杀进程计时器共用它；余量 `ONESHOT_MARGIN_MS = 15 s` 由它推出容量。这 15 s 要同时覆盖宿主在 spawn 前的身份判定（约 110 MB 摘要）、一次进程启动与收尾——够，但不富余，不要把它当成"只是嵌入的抖动余量"。这里还有一处必须写明的事实：本工作区里**没有任何代码消费 `ToolDefinition.timeoutMs` 去中断执行**（host 只校验它是正有限数），所以真正生效的边界是宿主自己的计时器——工具上那个声明是给宿主与未来机制看的，不能当作执行保障。单一来源因此落在常量上，而不是"工具的声明"。
- **上限判定先于模型加载**：子进程先读正本、算差异、比上限，超了就以退出码 4 退出（不加载模型、不嵌入）；否则加载模型、嵌入、单事务提交。所以"连它也放不下"的代价是**一次身份判定（约 110 MB 摘要，宿主在 spawn 前跑 `assertUsable()`）加一次进程启动**，而不是一次模型加载与嵌入——别把它写成"毫秒级"。
- 返回值：一行结果摘要（模式 / 文档数 / 嵌入数 / 耗时 / 当前语料），渲染成一句话。
- **常驻静默的实现钉死**：用 `private oneShotDepth = 0` 计数器，判定放在 `start()` 的**同步前段**（`assertUsable()` 旁边）抛 `busy`；**不要**把闸做成 `this.starting` 或 `this.stopping` 里的 promise——放进 `this.starting` 会让闸后的调用走"已有 starting"那条提前返回、根本不 spawn，随后在 `request()` 抛 `internal`；放进 `this.stopping` 会让 `stop()` 与 `dispose()` 跟着阻塞最多 10 min；判定放进 `start()` 的异步体则会产生无人处理的 rejection，触发宿主 fail-loud 的 `unhandledRejection` 而退出（`process.ts` 里 `assertUsable()` 的位置就是为这条留的）。闸在 `oneShot()` 里**先于** `await this.stop()` 置位、在 `finally` 里递减。
- **一次性子进程必须登记**（`private oneShotChildren: Set<ChildProcess>`），`stop()` 与 `dispose()` 一并杀它们的进程组。**用集合而不是单字段**：两个并发的一次性入口下，单字段会被后写者覆盖、先结束者的 `finally` 又把它置空，仍在跑的那个就失去引用、杀不到。（更简单的替代是让第二个并发的一次性请求直接以 `busy` 拒绝——spec 允许。）今天那个 child 只是局部变量、卸载不管它：旧窗口是 60 s，抬到 10 min 之后"卸载后没有残留子进程"这条承诺会破，而它持锁并写共享索引目录。
- **诊断工具可以覆盖上限**：`scripts/mem-profile.mjs` 要在一个可能超出常规上限的语料上初始化内存曲线，所以它显式设置 `ENGRAM_BRIDGE_MAX_DOCS`；否则会在初始化阶段直接以退出码 4 结束。
- `stop()` 要能按调用方指定错误类别：一次性入口那次停常驻用 `busy`，否则被静默打掉的在途检索会拿到 `internal`，而不是「正在更新」（D6 的等待策略讲的就是这个回答）。
- 退出码：`3` = 运行时或模型不可用（沿用）、`4` = 本次工作量超出上限（新）、其余 `1`。
- 宿主侧的两处实现细节：一次性子进程的杀进程计时器现在写死用 `this.options.timeoutMs`（默认 60 s），必须改用 `ONESHOT_TIMEOUT_MS`（**模型那条显式入口**；操作者命令走 D8 的无预算分支，不装计时器）；`childEnv()` 必须把 `ENGRAM_BRIDGE_MAX_DOCS` 传下去；`child.on('error')` 分支也要清计时器（现在只有 `'exit'` 清，spawn 失败会留下一个被引用的长计时器，测试进程会跟着挂）。
- 被否的变体：给常规检索加一个"允许等待"的参数。这条不是因为超时机制不可行（上面说了，声明本来就不被执行），而是因为它把"知情同意"藏进了一个布尔参数：模型看到的仍是一个会突然变慢的检索，而独立工具让"要多等几分钟"成为一次可被描述、可被拒绝的独立动作。

## D8 操作者路径：会话里的一条人类命令

**不用 shell 脚本。** 宿主有 `@deepseek-ai/dsh-commands`：插件注册一条**人类命令**，操作者在会话里敲它，它**不发给模型**，直接在宿主进程里执行，结果作为一段文本回到界面。`command/run` 与 `command/done` 是宿主自己声明的会话事件（所以不触碰硬规则 6 的"禁止新增未标记事件类型"），注册返回的正是"注销这一个定义"的 disposer（满足硬规则 2）。

接口以生成参考为准（`@deepseek-ai/dsh-commands/lib/types/index.d.ts` 与 `types.d.ts`）：`ctx.commands.register({ name, description, handler })`；handler 收到 `{ commandId, agent, rawInput, attachments, signal }`；返回 `{ kind: 'success'; text?: string } | { kind: 'error'; text: string }`（**`error` 的 `text` 必填**，`success` 的才是可选）；被取消或被抛出的 handler 由宿主结算成 `kind: 'error'`。

> **版本注记**：本机插件依赖树里是 `@deepseek-ai/dsh-commands@0.1.2-rc.1`，而实际运行插件的 host 是 `0.1.5-rc.1` 家族——本仓库六处 `@deepseek-ai/*` 的 pin 都落后于 host。这是**既有的、repo 级**的版本漂移，不在本变更内解决；本期只把新依赖 pin 在**与仓库其它六处相同**的版本上（类型检查内部一致），并靠任务 6.4 的真机步骤确认宿主那一版的行为。两版 `index.d.ts`/`types.d.ts` 的差异集中在 `attachments` 与 `input` 相关类型（`CommandInputDescriptor.images` → `attachments`、`attachments` 的元素类型放宽、`execute()` 的第三参改名），而**本插件用到的字段两版一致**（`name`/`description`/`handler`、`invocation.signal`/`agent`/`rawInput`、`CommandResult`）——所以按 `0.1.2-rc.1` 编译在今天的宿主上是安全的；一旦将来声明 `input` 或用到 `attachments` 的元素类型，`pnpm typecheck` 抓不到这个偏差，届时要重新对宿主版本。

**为什么它比脚本好**（同样的活，少一整类问题）：

| | shell 脚本 | 人类命令 |
|---|---|---|
| 谁在等 | 终端 | 会话界面（操作者知情） |
| 路径 / 模型目录 / 线程数 | 再写一遍，或塞一串环境变量 | 直接用插件已经拿到的配置 |
| 与常驻检索进程的关系 | **另一个互不相识的写入者**：要抢锁，还要担心常驻读到旧副本 | **同一个 manager**：先停常驻、走同一族一次性子进程（但走无上限的那条；干活仍是子进程——宿主不能加载嵌入运行时） |
| 取消 | Ctrl-C | 宿主给的 signal，贯通到子进程 |

**关键：这条路径必须真的不受单次预算约束。** 模型那条路（D7）带着两个上限——杀进程计时器 `ONESHOT_TIMEOUT_MS` 与 `ENGRAM_BRIDGE_MAX_DOCS = 7200`。而操作者路径存在的理由**正是"超出任何单次预算"那一档**，所以它不能复用带上限的那次 spawn：

- spawn 时**不装杀进程计时器**，并把 `ENGRAM_BRIDGE_MAX_DOCS` 写成显式的字面量 `unlimited`（编码见 D2；**不是缺省**——缺失按硬规则 4 响亮失败）；子进程因此不会以退出码 4 自我了断。锁不需要特殊取值：D6 的**进展心跳**让长跑在任何时长下都不会被判陈旧（这也是不用"无 TTL 哨兵"的原因——那会让 pid 复用变成永久阻塞）。
- 停止手段只有两个：操作者的取消信号（杀掉整个进程组）与插件卸载（`dispose()`）——所以它必须登记进 `oneShotChildren`（D7）。
- 具名方法 `oneShotUnbounded()`，与 `oneShot(policy)` 分开，避免"同一个方法两套上限"这种隐形分叉。**顺序与有界路径完全相同**：拿锁 → 读正本 → 算差异（不需要模型）→ 才加载模型。操作者路径把限额判定变成 no-op，但**不能**因此把"加载模型"提前——否则两个 16 线程进程会同时把模型读进内存，D6 的"只有一个在写、第二个在拿锁前不加载模型"就不成立了。

**其余决定：**

- **默认跑到完，不接受参数。** 操作者是知情等待，取消信号就是兜底；不给它加预算参数，也就没有第二个"预算"概念（与 D4/D7 一致）。
- **它不受 `searchEnabled` 约束。** 那个开关管的是**由模型发起**的检索与显式入口；这条请求是修复手段，可能正用在"先修好再打开"的场景里。spec 的开关那条已限定为"由模型发起的入口"，并把操作者请求单列成一条要求（含"开关关闭时仍可用"的场景）。
- **注册必须独立于工具声明。** 工具注册在 `registerTools()` 里，而那个函数在工具声明为空时会提前返回（冷 `tools.json` 时首个请求根本没有 engram 工具）。命令是修复手段，恰恰在这种状态下最需要它——所以它走自己的注册路径，**不依赖**任何 engram 工具声明。
- **可选依赖，别拖垮整座桥**：用 `ctx.inject(['commands'], (ctx) => …)` 做可选消费（cordis 把 `ctx.inject` 混进 `ctx`），没挂该服务的 profile 只是"没有这条命令"，而不是 engram-bridge 整体不激活；导出的 `inject` 保持 `['tools']`。**注意**：把 `commands` 写进导出的 `inject` 会让"缺该服务的 profile"里整个插件不加载（fiber 的每个注入名都必须有实现），那是把读层耦合到一个 UI 层服务上。
- **注册由 `ctx.inject(['commands'], …)` 回调里的那条 `ctx.effect` 拥有**（**必须建在子 ctx 上**：cordis 的 ctx 代理在取不到的服务属性上会**抛错**，在插件自己的 ctx 上写 `ctx.commands` 会让缺该服务的 profile 直接加载失败——正好是"可选消费"要避免的），**不要** push 进现有的 `disposers` 数组：那个数组在每次 `registerTools()` 时被**整体重新赋值**（不是 push），命令的注销器会被丢掉；而 `CommandRuntime.register` 的 effect 挂在服务自己的 ctx 上、不随插件 fiber 卸载——两者合起来意味着 profile 热重载后第二次 `apply()` 会撞 "already registered" 并使插件加载失败。`ctx.effect(() => ctx.commands.register(def), 'engram-bridge.command')` 的返回值就是注销器，cordis 会收集。
- **命令名**：定成 `engram-sync`（小写、不带斜杠、匹配宿主校验的 `^[a-z][a-z0-9_-]*$`）。它是外部可见的名字，**也是拒绝文案要指认的名字**，所以做成一个单一常量，供 `process.ts` 侧拼装超上限拒绝时引用。
- **`recordInput: false`**：这条命令不接受参数，不写它的话手敲的多余文本会被记进 `command/run.args`。
- **取消要真的贯通**：注册表的 abort 只停止等待、**不终止 handler**，而且 handler 的返回值会被丢弃（`execute()` 以 abort 错误 reject，宿主结算成 `command/done{kind:'error'}`）。所以 handler 必须自己观察 `invocation.signal`：杀一次性子进程的**进程组**、**等它退出**、再返回。这要求 manager 新增一个接受信号的入口（`oneShot(policy, signal?)`），并在协议里加一个"已取消"的失败类别（现有 `RecallErrorKind` 里没有）。
- **两条命令并行**：命令路径的锁等待取一个**固定短窗口（拟 5 s）**，拿不到就以「正在更新」拒绝。这是"让失败成为常态"的取舍（人手敲第二次时，"和第一次撞车"比"一起排队"更清楚），不是契约：窗口内第一次已完成的话，第二次当然可以照常完成。
- `ctx.commands` 的类型来自该包的模块增强，所以命令模块需要一句 type-only import（照本仓库对其它 `@deepseek-ai/*` 的惯例）。
- 命令名与描述是外部可见的（发现 UI 里会出现），定成小写、不带斜杠，并写进 README。

**唯一要现场验的一件事**：这个服务确实挂在 `web` profile 上并能跑完一次（声明文件存在 ≠ profile 里已加载）。

## D9 不动的部分

- **原子性**：拒绝不写任何东西；写入仍是单事务。
- **模型同代**：判定与"换代即重建"不变，只是重建现在也受同一限额约束（D5）。
- **运行时/模型缺失优先**：`assertInstalled()` / `assertUsable()` 在 spawn 之前，先于一切限额判定。
- **宿主 import 边界**：限额与政策都在 `process.ts`，不引入对嵌入运行时的静态引用（`pnpm check:boundary` 继续通过）。
- **常驻内存**：常驻仍按 `embedThreads` 起；高线程只出现在显式入口触发的短命进程里。
- **配置**：不新增键。`searchTimeoutMs` 仍是自动路径的预算旋钮。

## 被否的路

- **自动转交（三档）**：见 D3——它在"不想插入延迟"的前提下静默插入 8–51 s。
- **独立的 `toolBudgetMs`**：与 `ONESHOT_TIMEOUT_MS` 指同一件事，多一个名字就多一处漂移。
- **把 SQLite 自己的写锁当作唯一互斥**：`BEGIN IMMEDIATE` + `busy_timeout` 是纯 JS 的、内核仲裁的锁，持有者被 SIGKILL 时由内核释放，能一次性解掉 pid 存活 / TTL / 时钟回拨三套启发式。没选它是因为它盖不住"索引文件缺失/损坏、需要先销毁重建"那一档（那里没有可加锁的 DB），于是要么两套机制并存、要么让损坏态无锁。本期仍把锁文件作为唯一入口，同时配上 `busy_timeout` 与 `SQLITE_BUSY → busy` 归一，作为提交前的最后一道。
- **提高 `embedThreads`**：x86-64 上几乎免费，但 arm64 上要拿唯一已不合格的内存判据去换，且不解决全量重建。
- **背压 / 分块提交**：违反要求 1，必须改规格；显式入口不需要它。
- **嵌入结果落盘做断点续嵌**：能根治"被杀即零进展"，但引入第三个派生制品与它的失效判定（模型换代、语料删除、部分写入）；本期不做，记为下一步。
- **宿主侧 diff**：要把读正本与索引比对搬进宿主，重复一份逻辑并让宿主持有派生状态读句柄。
- **平台分支 / 每路径一套常数**：见 D4。
- **`tmp + rename`**：见 D6，本期不做。
- **写侧钩子 / 监视 engram**：engram 不提供，且违反既有的"无推送侧"设计。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| 修复依赖调用方行动：拒绝被吞掉 = 静默退化 | 拒绝文本与工具描述写成载荷（入口名 + 条数 + 预估秒数 + "完成后请重发"）；真机验收覆盖这条链路 |
| 常数偏乐观（更慢的机器）→ 活锁回来 | 常数取最差测量点再乘安全系数；记下退回条件与复测方法；拒绝文案把 `searchTimeoutMs` 作为自动路径的旋钮给出 |
| 显式入口占住一次调用最多 10 min（操作者命令更久） | 它是显式选择；上限判定先于模型加载，做不完的活不会先烧一次加载；取消/被杀后由**进展窗口**接管，活跃的长跑不会被误偷 |
| 一次性高线程进程的**瞬时峰值内存**没人量过（常驻判据 `1 线程稳态 ≤ 600 MB` 管不到它） | 本方案唯一未验的数。模式本身已存在，但频率与并发度变了——锁保证同时只有一个在**写**（进程可能有两个，但第二个在拿到锁之前不加载模型）。上线前量一次短命进程峰值；超标则降低 `rebuildThreads` |
| 加闸的位置写错会让宿主退出，或把显式入口自己锁死 | D7 把位置与三条反例钉死（同步前段 + 计数器；不碰 `starting`/`stopping`）；任务 5.3 的验证断言"闸期间发起检索 → `busy`、无无人处理的 rejection、无新的常驻启动" |
| 一次性子进程不在 `stop()`/`dispose()` 管辖内 → 卸载后最多 10 min 仍在写共享索引 | D7 要求登记进 `oneShotChildren: Set` 并在 `stop()`/`dispose()` 一并杀；任务 5.3 断言运行期间 `dispose()` 后该进程消失 |
| 新错误类别被 worker 的 kind 兜底吞成 `internal` | `worker.ts` 的 `errorKind()` 兜底只白名单了 `source-missing`，其余字符串一律 `internal`；任务 4.2 要求加显式分支，并在用例里断言 kind 不是 `internal` |
| 陈旧锁误判导致并发写 | pid 存活（快速路径）+ **进展窗口**（`lastProgressAt`/`staleAfterMs`）+ 时钟回拨判据；偷锁走原子 rename；按路径确认 token；**写事务内**复核 `(dev, ino)`/token/`source_hash` |
| 锁文件被用户删除或替换 | **写事务内**复核 `(dev, ino)` + token + `storedHash` 会放弃这次写入；"让内核代管"有纯 JS 候选（SQLite 自己的写锁），但盖不住"文件缺失/损坏"那一档，故仍以锁文件为唯一入口（见「被否的路」） |
| 跨进程只读侧陈旧（他人握着旧 inode） | 锁不覆盖；记入「已知未知」，可选后续是索引 generation |
| 单核机器上 `rebuildThreads = 1`，显式入口的并行优势消失 | 退化时仍能做完（只是慢）；上限按同一公式算出，诚实 |

## 迁移与回滚

- **无数据迁移**：派生索引的 schema、meta 键与 `algo_version` 都不变（改的是路由与并发，不是索引内容），升级后不需要重建。锁文件是运行时状态，不存在于旧版本。
- **行为变化**（可观察）：Δ 超出自动限额（默认 46 条）时，由"静默内联/超时"变为"明确拒绝 + 显式入口"；"索引不可信"不再自动转交子进程。
- **多 profile 是一处退化**：`README.md` 已写明，同一台机器上声明不同的两个版本会互相把对方的索引判为需要重建。现状是"每轮重建一次、还能答"；按本变更，大语料下会变成"每轮拒绝"（每个 profile 依次触发显式入口也只会互相覆盖）。这不是本次要修的问题（按身份分目录是另一条线），但它是可观察行为从"慢"变成"不可用"，必须在升级提示里保留"同一台机器所有 profile 保持同一版本"。
- **回滚**：回退代码即可；删掉可能残留的 `index.db.lock` 也无影响（陈旧锁会被接管）。索引不受影响。
- **验证方式**（对应 tasks）：用一份旧版生成且合法的派生索引跑一次检索，断言没有触发重建；断言配置键集合与迁移前一致（本变更不新增键）。
- **部署**：模型与运行时仍按 `AGENTS.md` 的显式安装步骤准备，本变更不新增安装项。

## 已知未知与退回条件

- **一次性进程峰值内存**：未测（见 Risks）。退回条件：在其宣称支持的最差机器上超出可接受范围 → 降低 `rebuildThreads`。
- **常数 `K` 的适用面**：来源是两台桌面级机器各一次读数。若目标机器实测慢于 K，活锁会回来 → 退回条件是**抬高 K**（宁可多拒绝），并记录新读数。
- **只读侧的跨进程陈旧**：另一个 profile 的常驻进程可能持续从被替换掉的旧索引作答。今天的代码不处理；本变更不加重也不解决。可选后续：索引 generation + 每次查询前便宜地比一次。
- **锁在网络盘上不在支持范围内**：pid 存活与三条钟表判据都**只在 `host` 一致时生效**（索引目录是本地派生状态，先按同机假设）。跨机时它们全部失效——尤其"读者时钟快几分钟"会把正在心跳的持有者判陈旧并偷锁，所以钟表判据一律加了 host 门控；跨机只剩人工处理（删锁文件），记为残留。
- **时钟回拨 + pid 复用 + 没有内核锁**：陈旧判据现在量的是"**多久没有进展证明**"（持有者每个嵌入批次心跳一次，窗口是常数，拟 5 min），所以 pid 复用与时钟回拨都不需要靠"大 TTL"兜底：同机的死持有者按 pid 立刻被接管，跨机或 pid 被复用的按窗口被接管，活跃的长跑永远不会被误偷。协议里另有 `now < lastProgressAt - ε`（且 host 与本机一致）兜时钟回拨。Node 内建没有 `flock`，但纯 JS 的内核级候选是 SQLite 自己的写锁（见「被否的路」）。本期靠"pid 存活 + 进展窗口 + 时钟回拨 + 写事务内 `(dev, ino)`/token/`source_hash` 复核"。
- **锁文件被手动删除或替换**：**写事务内**的复核会发现并放弃这次写入。代价按路径不同：有界路径白做一次嵌入；**操作者路径白做的是整段运行**（可能几小时）——这也是心跳窗口取得偏保守、pid 判据优先的原因。这是"用户删派生状态"这条既有自由度带来的必然残留，不当作缺陷修。
- **限额以"条"为单位，而单条成本有硬上界**：截断在 `model_max_length`（默认 512）处（见 D4），所以长度推不动成本；最坏（全部触顶）相对标定均值的偏斜约 1.18×，而**显式入口那一档的余量只有 1.27×**（安全系数本身，还要覆盖身份判定与进程启停）。退回条件：复测时记录**触顶比例**；若几乎全触顶则抬高 K，或把 16 线程那条读数改在全触顶语料上取。
- **`scripts/mem-profile.mjs` 需要跟着改**：它现在用 `worker.js --rebuild` 做初始化，并只量常驻稳态。保留 `--rebuild`（D7）让它不坏，但要量一次性进程峰值，该脚本需要新增一条一次性子进程的 RSS 采样路径（对应 tasks 8.2）。
- **`embedThreads` 没有上界，而内存判据只在 1 线程量过**：schema 只有 `min(1)`，所以用户能配 64；公式侧的夹取（D4）保证限额不因此变乐观，但常驻 RSS 会跟着涨，而 `1 线程稳态 ≤ 600 MB` 这条判据对更高线程数没有读数。本期不改配置语义（本变更承诺不新增键、不改既有键的行为），只在构造 manager 前对 `embedThreads > 16` 打一条 `warn`（说明：更高的线程数不提高自动限额，且抬高常驻内存），并把"更高线程数的常驻内存"记为未测。
- **是否用实测速率自适应回填上限**：worker 的计量里已有 `embedDocs` 与耗时，理论上可把观测速率回报给限额。收益是免去手工常数，代价是多一份可写状态与"观测偏差 → 乐观上限 → 活锁"的新失败模式。本期不做。
- **显式入口的调用超时取值**：拟 10 min（上限约 7200 条）。取值需要一次真实大积压的验收来确认，而不是拍定。
